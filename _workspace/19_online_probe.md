# 19. 온라인 실시간 조회 — 실현성 조사와 판정 근거

**조사일 2026-08-31.** 온라인 사용처 키워드 검색이 "삼성전자 비스포크 로봇청소기" 같은 상품명에 답하지 못하는 문제(태그 기반 `indexOf` 단일 부분문자열이라 공백이 들면 무조건 0곳)를 실시간 조회로 풀 수 있는지 실측했다. 결론과 설계는 ADR-17.

이 문서는 **코드보다 먼저 쓰인다.** 여기 적힌 실측값이 `ProbeTargets`의 규칙과 테스트 픽스처의 근거이며, 몰이 개편되면 이 표와 실제가 어긋나는 것으로 드러난다.

## 1. 22곳 실현성 조사

`app` 컨테이너는 `eclipse-temurin:21-jre` — 브라우저가 없다. 따라서 **정적 HTTP 응답에 검색 결과가 실리는 몰만** 실시간 조회 대상이 된다. 22곳 홈에서 검색 폼을 추출하고, 추출된 곳에 실제 검색 요청을 보내 판정했다.

## 2. robots.txt 검토 (2026-08-31)

저장소에 robots.txt를 검토한 기록이 없었다. 이번에 처음 확인했고, **그 결과로 2곳을 제외했다.**

| 몰 | robots.txt | 검색 경로 | 판정 |
|---|---|---|---|
| onnuri-hotdeal | `Allow: /` + `Disallow: /api/, /checkout/komsco-return` | `/search` | **허용** |
| onnuri-chance | `Disallow: /include/` | `/` | **허용** |
| onnuri-sijang | HTTP 404 (파일 없음) | — | **명시적 금지 없음** |
| onnuri-market | `User-agent: *` `Allow: /` | `/shop/search_product.php` | **허용** |
| onnuri-gonggong-mall | 그누보드 계열 다수 Disallow(`/adm/ /bbs/ /shop/cart.php` 등) — **`/shop/search.php`는 목록에 없음** | `/shop/search.php` | **허용** |
| epost-mall | `Disallow: /upload/, /*file*, /*File*, /*adm*` | `/fo/search/search.do` | **허용** |
| **onnuri-goodday** | **`Disallow: /` + `Allow: /$`** | — | **차단 — 제외** |
| **inthemarket-onnuri** | **`Disallow: /` + `Allow: /$`** | — | **차단 — 제외** |

`Disallow: /` + `Allow: /$` 는 **홈 문서 하나만 허용하고 나머지 전부 차단**이라는 뜻이다. 기술적으로는 검색이 되지만 조회하지 않는다.

**런타임 robots 조회는 하지 않는다** — 이용자 요청마다 robots.txt를 함께 받으면 아웃바운드가 2배가 되어 부담 억제 목표에 역행한다. 대신 야간 배치가 하루 1회 재조회해 변화만 리포트한다.

## 3. 판정 근거 — 왜 키워드 카운트로는 안 되는가

### 검색어 에코가 상품으로 오인된다

7개 몰 × 4개 질의로 재봤다. 응답에 검색어가 있다고 상품이 있는 것이 아니다.

| 질의 | 몰 | 토큰 히트 | 실제 |
|---|---|---|---|
| 삼성전자 비스포크 로봇청소기 | onnuri-goodday | 1 · 1 · 1 | **에코만** — `"비스포크 로봇청소기 검색결과"` 제목에 검색어가 박혔다. 상품 없음 |
| 삼성전자 비스포크 로봇청소기 | onnuri-gonggong-mall | 3 · 2 · **29** | 실제 상품 다수 |
| 삼성전자 비스포크 로봇청소기 | onnuri-market | 0 · 0 · 0 | 진짜 없음 |
| 다이슨 청소기 | onnuri-hotdeal | **21** · 7 | 실제 상품 |
| 다이슨 청소기 | onnuri-market | 0 · 0 | 진짜 없음 |
| 로보락 큐레보 | onnuri-gonggong-mall | 4 · 1 → `로보락 로봇청소기 호환 리필 물걸레 S5Max` | **부분 매칭 오탐** — 본체가 아니라 소모품 |

**"0이면 없다"는 신뢰할 수 있고, "0이 아니면 있다"는 신뢰할 수 없다.** 이 비대칭이 설계의 축이다. 히트 1~3은 에코 구간, 20회 이상은 실제 상품일 가능성이 높지만 경계는 몰마다 다르다.

### 다중 토큰 질의는 각 몰 검색엔진이 받아준다

"삼성전자 비스포크 로봇청소기"처럼 공백이 든 질의도 대부분 토큰 OR/부분 매칭으로 처리된다. 즉 **검색어를 우리가 쪼개 보낼 필요가 없다.** 다만 그래서 오탐(소모품·유사품)이 늘어난다.

## 4. "결과 없음" 문구 사전 (2026-08-31 실측 원문)

존재하지 않는 키워드(`zzqqxyw12345`)로 조회해 각 몰의 없음 문구를 수집했다. **이것이 판정 1순위 신호다.**

### 등급 A — 검색어 바인딩형 (단독으로 `none` 확정)

문구 안에 검색어가 들어가므로 약관·푸터가 구조적으로 걸릴 수 없다.

| 몰 | 실측 원문 |
|---|---|
| onnuri-hotdeal | `"zzqqxyw12345" 검색 결과 검색 결과가 없습니다` |
| onnuri-sijang | `검색하신 ' zzqqxyw12345 '에 대한 검색결과가 없습니다` |
| onnuri-gonggong-mall | `'zzqqxyw12345' 에 대한 0 개의 검색결과` / `등록된 상품이 없습니다` |

`onnuri-sijang`이 따옴표 안쪽에 공백을 넣는다(`' zzqqxyw12345 '`). 정확 일치로 매칭하면 깨지므로 **토큰 사이 `\s*`를 허용하는 유연 매처**로 컴파일해야 한다.
`onnuri-gonggong-mall`은 건수를 명시(`0 개의 검색결과`)해 가장 견고하다.

### 등급 B — 검색어 비의존형 (단독 확정 금지)

| 몰 | 실측 원문 |
|---|---|
| epost-mall | `고객님께서 찾으시는 검색결과가 없습니다` / `해당하는 상품이 없습니다` |

문구 매치 **+ 토큰 카운트 임계 미만**일 때만 `none`으로 친다. 둘이 어긋나면(문구도 있는데 상품 신호도 강함) `unclear` + 경고 — 몰이 "결과 없음" 배너를 상시 노출하도록 개편된 신호다.

### 등급 C — 사전을 두지 않음

| 몰 | 이유 (실측 원문) |
|---|---|
| onnuri-chance | 명시적 없음 문구가 검출되지 않았다. 잡힌 것은 `원산지 데이터 없음` — 상품 영역 밖 필터 UI 문구라 채택 불가 |
| onnuri-market | ⚠ **검출된 것이 전부 이용약관 문구다** — `③ 적립금은 현금으로 환급될 수 없습니다`, `다만 "몰"이 고의ㆍ과실이 없음을 입증한 경우에는 그러하지 아니합니다`. 페이지 전체에 문자열 매칭하면 **항상 "없음"으로 판정된다** |

`onnuri-market` 사례가 이 저장소가 반복해서 경계해 온 **"에러 없이 다른 답"**의 전형이다. 이 두 곳은 사전을 비워 두고 토큰 카운트로만 판정하며 신뢰도를 낮게 표시한다.

## 5. 상품명 추출 — 몰별 파서가 필요하다

범용 링크 패턴(`href`에 product/goods/item/prd 포함 + 링크 텍스트)으로 3개 몰을 시도했으나 **전부 0건**이었다. 마크업이 제각각이다.

키워드+가격이 같은 줄에 있는 스니펫 방식은 `onnuri-hotdeal`만 잘 나온다.

```
[로보락] Qrevo Edge 2 로봇청소기 · 공구의거리 · 30% · 1,190,000원
에브리봇 침구로봇청소기 X1 · 안양호계종합시장 · 10% · 269,000원
에브리봇 2026년 신상 로봇청소기 Q3 Turbo Plus · 안양호계종합시장 · 20% · 399,000원
[JONR] 로봇청소기 올인원 자동세척 건조 스테이션 T5 Pro Gen 2 · 공구의거리 · 499,000원
```

나머지 3곳은 0건. 따라서 **상품명 추출은 몰별 정규식이 필요하고, 그건 ADR-6이 기각한 "구조 변경에 취약"에 해당한다.**

→ 그래서 상품명 추출을 **판정 경로 밖에** 둔다. 깨져도 "근거 없는 `likely`"로 품질만 떨어지고 오답이 되지 않는다. 자세한 것은 ADR-17.

### 5-1. 몰별 상품명 정규식 (5단계에서 실측·배선, 2026-08-31)

1단계에서 `ProbeTarget.titlePattern` 을 **선언만 하고 6곳 모두 `null` 로 둔 채** 넘어갔다. 그래서 화면에 카운트만 남고 근거가 하나도 없었다 — 설계의 절반이 비어 있었던 셈이다(공공몰 `timeoutMs` 를 3단계에서 뒤늦게 배선한 것과 같은 유형). 5단계 렌더 검증에서 샘플이 0건인 것을 보고 발견했다.

6곳 검색 결과 HTML을 "김치"로 다시 받아 마크업을 확인했다.

| 몰 | 상품명 마크업 | 매치 / 질의어 포함 |
|---|---|---|
| onnuri-hotdeal | `<p class="… line-clamp-2 … text-card-foreground">` | 20 / 20 |
| onnuri-chance | `<li data-pcode=… data-pname="상품명">` | 19 / 19 |
| onnuri-sijang | `<p class="text"><strong></strong>상품명</p>` | 40 / 28 |
| onnuri-market | `<a href="…item.php?it_id=…">상품명</a>` | 21 / 21 |
| onnuri-gonggong-mall | `<h4 class="nl-name"><b>상품명</b>` | 20 / 20 |
| epost-mall | `<div class="goods_text"><p class="tit">상품명</p>` | 17 / 11 |

`onnuri-sijang`·`epost-mall` 에서 두 숫자가 벌어지는 것은 추천·연관 상품이 함께 실리기 때문이고(우체국은 `MALL_WIDE` 라 더 심하다), `ProbeJudge.extractTitles` 가 **질의 토큰을 포함하는 것만** 남겨 걸러낸다. `onnuri-chance` 의 `data-pname` 은 마크업 변화에 가장 둔감하다.

회귀는 픽스처로 고정했다 — 히트 픽스처에서 질의어를 담은 이름이 나오고, **없음 픽스처에서는 하나도 나오지 않는다**(샘플이 나오면 판정이 `likely` 로 기울어 "없는데 있다"가 된다).

### 5-2. 부분 일치를 부분 일치라고 말한다 (2026-08-31 라이브에서 적발)

배포 직후 `다이슨 청소기` 로 조회하니 온누리공공몰이 `likely` 에 이런 근거를 냈다.

```
진공 청소기 20L 대용량 상업용청소기 대형청소기 공장청소기
스틱 무선청소기 필터청소기 충전식청소기 소형진공청소기
```

HTML 을 세어 보니 상품명 20건이 **전부 '청소기'만 맞고 다이슨은 하나도 없었다.** 화면은 "관련 상품이 검색됨"과 함께 이 이름들을 내밀고, 이용자는 **"공공몰에 다이슨이 있다"** 로 읽는다. 계획서가 경계한 "로보락 큐레보 → 호환 리필 물걸레"와 같은 유형이고, 그보다 나쁘다 — 그건 최소한 로보락이었다.

두 가지를 고쳤다.

1. **정렬** — 후보를 다 모은 뒤 질의 낱말을 많이 담은 것부터 3건. 앞에서 자르면 질의 전체를 담은 이름이 있어도 잘려 나간다.
2. **표시** — 어떤 후보도 질의 낱말을 전부 담지 못하면 `samplePartial=true` 를 실어 보내고, 화면이 `검색어의 일부 낱말만 맞는 결과입니다 — 찾는 상품이 아닐 수 있습니다.` 로 바꿔 말한다.

**판정(status)은 낮추지 않았다.** 낮추면 `titlePattern` 이 없거나 깨진 몰에서 판정이 샘플에 끌려다니게 되고, "샘플은 판정 경로 밖"이라는 원칙이 무너진다. 샘플은 사실만 전하고 해석은 화면이 한다.

## 6-2. 검색 링크 (4단계, 2026-08-31)

실시간 조회는 6곳뿐이지만 **링크는 더 넓게 준다.** "확인하지 않았다"고 말하면서 갈 곳을 주지 않으면 이용자는 결국 "없다"로 읽기 때문이다.

**링크는 robots.txt 대상이 아니다** — 우리가 자동으로 긁는 것이 아니라 사람이 클릭해 들어가는 정상 이용이다. 그래서 자동 조회가 막힌 2곳도 링크는 넣는다.

| 구분 | 곳 | 비고 |
|---|---|---|
| 실시간 조회 대상 | 6 | 코드(`ProbeTargets`)와 데이터(`search_url_template`)에 같은 값 — 테스트가 대조한다 |
| robots 로 자동조회는 막히나 링크는 정상 | 2 | 온누리굿데이·인더마켓 |
| ~~검색은 되나 판정 규칙 미실측~~ | ~~1~~ | ~~꾹AI온누리몰~~ → **2026-09-01 조회 대상으로 승격**(6-5절). 당시 "`?keyword=` 로 김치 7회 확인"은 **오판이었다** — 그 7회는 카테고리 메뉴의 '김치·반찬'이었고 검색은 실행조차 되지 않았다 |
| **검색 URL 보유 합계** | ~~9~~ → ~~14~~ → **15** | 2026-09-01 재조사로 5곳(6-6절), 2026-09-02 온누리쇼핑 1곳(6-8절) |
| 홈으로 보내는 쇼핑몰 | ~~13~~ → ~~8~~ → 7 | 검색 폼이 없거나(4곳) 제출해도 URL 이 바뀌지 않는다(3곳). 롯데ON 은 범위 밖이라 의도적으로 홈으로 |

`search_url_template` 은 `note`·`region_limited` 와 같은 **큐레이션 필드**다. 야간 배치(단계 B)의 UPDATE 는 갱신 컬럼을 명시적으로 나열하는 방식이라 이 컬럼을 건드리지 않는다 — 계획 단계에서 "빠뜨리면 다음 00:30 에 NULL 이 된다"고 우려했으나 실제로는 자동 보존된다. 다만 다음 사람이 UPDATE 에 컬럼을 더할 때 실수하지 않도록 주석을 남겼다.

### robots.txt 재조회 (매일, 8곳)

조회 대상 전부 + 차단이라 제외한 몰. 제외한 곳도 계속 본다 — 풀리면 커버리지를 넓힐 수 있고, 아무도 다시 확인하지 않으면 영영 모른다.

2026-08-31 재조회: 8곳 전부 조사 시점과 동일(굿데이·인더마켓만 `Disallow: /`, 온누리시장은 404 = 금지 없음).

⚠ **감시 도메인을 손으로 적었다가 사고가 날 뻔했다.** 배치 상수에 굿데이를 `onnurigoodday.com`(실제는 `onnurigood.com`)으로 잘못 적었는데, **그 엉뚱한 도메인이 마침 `Disallow: /` 라 기대치와 맞아떨어져 통과했다.** 감시 대상이 조용히 다른 사이트가 되는 것이다. 그래서 도메인은 상수로 두지 않고 `data/online_platforms.json` 의 `search_url_template`(없으면 `url`) 에서 뽑는다 — 주소의 출처는 하나여야 한다.

## 6-4. 조회하지 않는 16곳의 사유를 화면에 말한다 (2026-09-01)

"확인하지 않았습니다"만 던지면 이용자는 그 이유를 우리 사정으로 읽거나, 나쁘게는 "없다"로 읽는다. 1절 조사표의 사유를 세 갈래로 묶어 `ProbeTargets.exclusionReason()` 이 돌려주고, 화면이 사유별로 곳 수와 함께 설명한다.

| 사유 | 곳 | 화면 문구 |
|---|---|---|
| `no-static-search` | 13 | 검색 결과가 화면에서만 만들어져 자동으로 읽을 수 없습니다. |
| `robots-blocked` | 2 | 이 몰은 robots.txt로 자동 조회를 막아 뒀습니다. **링크로 들어가 직접 검색하는 것은 정상 이용입니다.** |

(2026-09-01 꾹AI 승격으로 `rules-unverified` 는 쓰이지 않게 되어 제거했다 — 6-5절.)

robots 항목에 마지막 문장을 붙이는 이유는 6-2절과 같다 — **링크는 robots.txt 대상이 아니다.** 그 구분을 말하지 않으면 이용자가 "여기는 쓰면 안 되는 몰"로 오해한다.

테스트가 조회 대상 6곳과 제외 사전이 겹치지 않는지 확인한다. 겹치면 "조회했는데 조회하지 않은 사유가 붙은" 모순이 생긴다.

## 6-5. 꾹AI온누리몰 승격 — 4단계 오판 정정 (2026-09-01)

화면의 "확인하지 않은 1곳"을 조회 대상으로 만들 수 있는지 물어 재조사했고, **4단계 판단이 틀렸다는 것부터 드러났다.**

### 무엇이 틀렸나

4단계에서 `https://onnuri.ai/search?keyword={q}` 로 "김치"를 조회해 7회 잡히는 것을 보고 "검색은 된다"고 판단해 링크를 넣었다. 다시 세어 보니 그 7회는 전부 **카테고리 메뉴와 셀렉트 옵션의 '김치·반찬'**이었다.

```
<li><a href="/category?k_catecno1=5">김치·반찬</a>
<option value="5">김치·반찬</option>
```

결정적 대조: 있는 말과 없는 말의 응답에서 **상품 링크 20개가 완전히 같았고, 두 응답의 차이는 로그인 링크의 return URL 한 줄뿐**이었다. 존재하지 않는 파라미터(`k_keyword`)를 줘도 같은 결과가 나왔다 — 서버가 검색어를 아예 무시한 것이다. 브라우저로 열어도 검색창이 비고 결과가 바뀌지 않았다.

**1단계에서 "검색어 에코를 상품으로 오인하지 않는다"를 설계 축으로 세워 놓고, 4단계에서 토큰 카운트만 보고 스스로 그 함정에 빠졌다.** 그 결과 이용자를 검색이 실행되지 않는 화면으로 보내는 링크가 라이브에 나가 있었다.

### 올바른 URL

실제 검색 폼을 브라우저에서 제출해 보니 **`keytype` 이 필수**였다.

```
https://onnuri.ai/search?k_order=3&page_num=50
  &keytype=productname%3Aproductcode%3Acomment&keyword={q}
```

| 질의 | 응답 | 상품 |
|---|---|---|
| 김치 | 93,345바이트 | 50 |
| 로봇청소기 | 69,699바이트 | 17 |
| zzqqxyw12345 | 56,629바이트 | **0** |

### 판정 규칙

- **robots.txt**: `User-agent: *` → `Allow: /`. 금지는 `/BillgatePay`·`/callbacks`·`/sian`·`/api`·`/login` 이고 `/search` 는 허용. `GPTBot`·`ChatGPT-User`·`OAI-SearchBot` 만 전면 차단인데 우리 UA 는 해당하지 않는다. **`/api` 가 금지이므로 내부 API 를 직접 부르는 길은 애초에 막혀 있다** — 화면 검색 URL 을 쓰는 것이 유일하고 정당한 경로다.
- **없음-문구(등급 B)**: `등록된 상품이 없습니다.` 있음 응답에는 없다(온누리마켓 같은 약관 상시 노출이 아님을 대조 확인).
- **`echoesQuery = false`**: 검색어가 `href`·`input value` 에는 박히지만 **화면 텍스트로는 되뿌리지 않는다.** 처음엔 원본 HTML 에서 24회를 세고 `true` 로 선언했는데 **카나리아가 선언(true)과 실측(false)의 차이를 잡아냈다.** 정정하면 토큰 0 판정을 쓸 수 있어 '없다'를 확정할 수단이 하나 더 생긴다. 카나리아를 둔 값을 첫날 회수한 셈이다.
- **titlePattern**: `<p class="pro_title">상품명</p>` — "로봇청소기" 조회에서 17건 전부 질의어 포함.

### 결과

조회 대상 **6곳 → 7곳**, 확인하지 않는 곳 16 → 15. 카나리아 14건 전부 기대치 일치. `rules-unverified` 사유는 이제 어느 몰에도 붙지 않아 상수와 화면 문구에서 제거했다.

## 6-6. 나머지 13곳 폼 제출 재조사 (2026-09-01)

꾹AI에서 통한 방법 — **실제 검색 폼을 브라우저에서 제출해 이동 URL을 본다** — 을 나머지 13곳에 그대로 적용했다.

### 또 같은 함정에 걸릴 뻔했다

현대이지웰은 "김치 21회 / 없는 말 4회"라 얼핏 검색이 되는 것처럼 보였다. 실제로는 **21회가 전부 햄버거 전체메뉴의 `반찬/즉석식>김치`·`배추김치`** 였고, 본문에는 `fn_getGoodsSearch(1)` 만 있었다 — 상품은 그 뒤 JS 가 가져온다. 꾹AI 와 **똑같은 구조**다(6-5절). 이번에는 응답 길이가 1.45MB 로 같은데 히트만 다른 점을 이상하게 봐서 걸러냈다.

교훈은 4단계와 같다. **토큰 카운트는 검색 성공의 증거가 아니다.** 길이차와 상품 마크업을 함께 봐야 하고, 가장 확실한 것은 없는 말과의 대조다.

### 롯데ON 을 링크에서도 뺀 이유

기술적으로는 조회가 된다(311 / 8). 그러나 ①`robots.txt` 가 `Disallow: /` 이고 ②이동 URL 이 **롯데ON 전체 검색**(`mallId=1`)이라 온누리 상생스토어 밖 상품이 대부분이다. 2026-08-21 롯데ON 딥링크가 호스트 몰 GNB 를 통째로 끌고 온 사고와 같은 성격이다. 링크를 주면 이용자가 **온누리상품권으로 살 수 없는 상품**을 보게 되므로 홈으로 보낸다.

반대로 온누리팔도시장은 robots 가 자동 조회를 막았을 뿐 **링크는 robots 대상이 아니므로**(6-2절) 링크는 준다. `/Goods/` 와 `/goods/` 는 대소문자만 다르지만 의도가 명백하므로 우회하지 않는다.

### 결과

검색 링크 보유 **9곳 → 14곳**(2026-09-02 온누리쇼핑까지 15곳 — 6-8절). 확인하지 않는 곳 중 링크가 있는 곳이 그만큼 늘었다.

## 6-7. 화면에서 결과가 만들어지던 몰 — 내부 API 로 편입 (2026-09-02)

`no-static-search` 13곳도 조회할 수 없느냐는 요청. **브라우저를 들이지 않고 풀었다.**

"화면에서 결과가 만들어진다"는 것은 JS 가 어딘가로 요청을 보낸다는 뜻이다. 그 요청은 정적 HTTP 로 그대로 재현할 수 있다. 공식 화면이 보내는 것과 **같은 요청**이므로 새 경로를 만든 것도, 제약을 우회한 것도 아니다.

### robots 가 먼저 4곳을 걸러냈다

| 몰 | robots | 판정 |
|---|---|---|
| 11번가 온누리마켓 · 현대홈쇼핑 | `Disallow: /` | 제외 |
| 사이소 | `Disallow: /api/` | 내부 API 불가(화면 경로는 봇 차단으로 1.7KB) |
| 공영쇼핑 | `Disallow: /search/` · `/api/` | 제외 |

### 남은 7곳 XHR 관찰 → 2곳 편입

| 몰 | 결과 |
|---|---|
| **현대이지웰 온누리전통시장** | `GET /onnuri/main/searchList?searchTerm={qq}&displaySize=50&…` **편입** |
| **온누리5일장** | `POST api.samaint.co.kr/main/product_search_cate` (form) **편입** |
| **온누리쇼핑** | `GET /search?searchWrd={q}` **편입**(재시도에서 발견 — 6-8절) |
| 지니어스몰 · 시장을 방으로 | 검색 input 자체가 없다 |
| 인어교주해적단 · 온누리 놀장 | input 은 있으나 질의어를 담은 XHR 이 잡히지 않음 |

### 두 몰이 기존 구조를 벗어난 지점

1. **이중 인코딩** — 이지웰은 `searchTerm` 을 두 번 인코딩해 받는다(`%25EA%25B9%2580…`). 한 번만 하면 0건이다. `ProbeUrl` 에 `{qq}` 자리를 만들었다.
2. **form POST** — 5일장은 GET 이 아니라 form 본문을 받는다. `ProbeTarget.formBody` 를 더하고(기존 7곳은 보조 생성자로 무수정) `ProbeFetcher` 가 분기한다.
3. **`cate_gno=45` 가 검색이다.** `all` 을 쓰면 **검색을 무시하고 전체 목록**을 준다 — 없는 질의에도 578KB 가 온다. 그대로 뒀으면 이 몰은 무엇을 묻든 늘 '있음'이 됐을 것이다.
4. **판정 엔진은 고치지 않았다.** 정규식 기반이라 JSON 응답에도 그대로 동작한다 — 상품명이 `"GDS_NM":"…"` / `"product_name":"…"` 일 뿐이다.

### 카나리아가 첫날 또 잡았다

`ProbeJudge` 의 "본문 500자 미만이면 unknown" 가드는 **화면 HTML 을 전제로** 만든 것이다. 내부 API 는 **결과가 없을 때 정상 응답이 짧다** — 이지웰의 '없음' 응답이 316자다. 같은 기준을 들이대면 확실한 '없음'을 unknown 으로 뭉갠다. 카나리아가 `absent 기대=none 실제=unknown` 으로 잡아냈고, API 몰만 하한을 60자로 낮췄다(빈 응답·에러 페이지는 여전히 걸러야 하므로 없애지는 않았다).

### 이용자 링크를 JSON 으로 주지 않는다

`searchUrlFor` 는 조회 대상이면 **조회 URL 을 링크로 쓰고 있었다.** 그대로 뒀으면 이 두 몰의 이용자가 JSON 화면을 마주한다. **데이터의 `search_url_template`(사람이 볼 화면)을 먼저 쓰도록** 순서를 뒤집었다. 계약 테스트도 "코드 URL 과 데이터 URL 이 같아야 한다"에서 **"화면으로 조회하면 일치해야 하고, API 로 조회하면 데이터에 사람이 볼 링크가 반드시 있어야 한다"**로 바꿨다.

### 결과

조회 대상 **7곳 → 9곳**(재시도로 10곳, 6-8절), 확인하지 않는 곳 15 → 12. 카나리아 20건 전부 기대치 일치.

| 몰 | absent | present | 샘플 |
|---|---|---|---|
| 현대이지웰 | none (316자) | likely (히트 114) | 3 |
| 온누리5일장 | none (2,450자) | likely (히트 161) | 3 |

## 6-8. 남은 5곳 재시도 — 온누리쇼핑 편입 (2026-09-02)

앞선 관찰에서 "검색 input 없음"·"XHR 없음"으로 접었던 5곳을 다시 봤다. **접근을 바꾸니 하나가 열렸다.**

무엇을 달리했나 — ①숨은 input 까지 열거 ②돋보기·검색 버튼을 눌러 UI 를 **열어 본 뒤** 찾기 ③XHR 뿐 아니라 **document 요청**까지 관찰 ④JS 번들에서 API 경로 문자열 검색.

| 몰 | 결과 |
|---|---|
| **온누리쇼핑** | **편입** — 검색 UI 가 클릭으로 열려 폼을 못 찾았을 뿐, 결과는 **서버가 렌더한다**. `/search?searchWrd={q}` |
| 인어교주해적단 | 앞서 잡은 `name=query` 는 **구글 번역 위젯**(`goog-gt-votingInputSrcText`)이었다. 실제 검색 UI 요소가 0개다 |
| 지니어스몰 | 숨은 것까지 포함해 검색 input 0개 — 검색 기능이 없다 |
| 시장을 방으로 | input 0개(배달 주소 선택 선행 구조 — 2026-08-21 기록과 동일) |
| 온누리 놀장 | 검색창은 열리나 **키 입력이 들어가지 않는다.** 번들의 `/api/v1/search/...` 경로는 직접 부르면 404. 시장·매장 선택이 선행되는 구조로 보인다 |

### 온누리쇼핑 규칙

- robots.txt: 전면 차단 없음, `/search` 금지 없음
- 없음-문구: `검색된 상품이 없습니다.` — 있음 응답에는 없다(대조 확인) → 등급 B
- titlePattern: `<div class="name">상품명</div>`
- **`echoesQuery=false`** — 검색어가 `<input value>` 와 JS 변수에만 있어 `stripEcho` 후 텍스트에는 남지 않는다. **카나리아가 선언 true 와 실측 false 의 차이를 또 잡았다**(이지웰에 이어 두 번째). 정정하니 토큰 0 판정도 함께 쓸 수 있게 됐다.
- 실측: 김치 126회·64KB · 로봇청소기 105회·60KB · 없는 말 3회·15KB(전부 검색창 에코)

### 결과

조회 대상 **10곳**, 확인하지 않는 곳 **12곳**. 카나리아 20건 전부 기대치 일치.

## 7. 재조사 방법

이 문서의 표는 시간이 지나면 낡는다. 재조사는 카나리아(`/api/online/search/selftest`)가 매일 자동으로 하고, 전면 재조사가 필요하면 다음 순서로 한다.

1. 22곳 홈 HTML에서 `<form>` 중 검색 폼 추출(action + input name)
2. 추출된 URL 템플릿으로 "실제 키워드"와 "없는 키워드"를 각각 조회
3. 태그 제거 후 키워드 히트·응답 길이차 비교 → 실현성 판정
4. 없는 키워드 응답에서 "없습니다/없음/찾을 수 없" 주변 문장 수집 → 문구 사전 갱신
5. robots.txt 재확인 → 차단된 몰 제외
6. `ProbeTargets`와 이 문서를 함께 갱신하고 `measuredOn`·`robotsCheckedOn`을 올린다

## 6-9. 지니어스몰 승격(11곳) + 전일 색인 층 신설 (2026-09-02)

남은 12곳을 더 열 방법을 전수 검토했다(`20_probe_expansion_analysis.md`, ADR-18). 결론은 "병목은 브라우저가 아니라 robots 와 범위" — 12곳 중 8곳은 robots, 2곳은 시장·주소 선택 선행, 1곳은 검색 API 인증(인어교주해적단), 그리고 1곳은 **판정이 틀려 있었다.**

### 지니어스몰 — "검색 기능 없음"이 틀렸다

6-8절의 "검색 input 0개"는 **홈**에 폼이 없다는 관찰이었고, 20절 5절의 4변형(`keyword`·`search_text`…)은 파라미터 이름을 지어내 시험한 것이었다. 실제 폼은 **상품 목록 페이지 안**에 있다 — `<form class="search_bbs" action="/product/product.html" method="GET">` + `name="search"`. 색인 크롤러를 만들던 중 발견했다.

| 질의 | 응답 | 판정 |
|---|---|---|
| 로봇청소기 | 200 · 50,936B · `총 <i>12</i>개` · `<em>` 12개 = 상품 수 | likely (히트 21 · 샘플 3) |
| zzqqxyw12345 | 200 · 29,844B · `총 <i>0</i>개` · `<em>` 0개 | none (high) |
| 김치 | 0건 — 가전 전문몰 | none |

- URL `https://luxurysystem.co.kr/product/product.html?search={q}`, robots `Allow: /`·`Disallow: /ko_mall/`(`/product/` 허용)
- 없음-문구: 태그 제거 후 형태 **`총 0 개의 상품이 있습니다`**(등급 B — 있음 응답에는 그 자리에 건수가 찍혀 구조적으로 함께 나올 수 없음, 테스트로 고정). 원문 `총 <i>0</i>개` 형태로는 절대 매치되지 않는다 — 판정 엔진은 `toText` 뒤에 문구를 댄다.
- titlePattern `<em>([^<]+)</em>` — 상품명에 class 가 없고 목록 밖에서 `<em>` 을 쓰지 않는다(있음 12 / 없음 0 으로 확인)
- echoesQuery **false** — 검색어가 `<input value>` 에만 남아 stripEcho 후 토큰 0
- 카나리아 present 질의는 `로봇청소기`(김치는 0건이라 쓸 수 없다). 요청량 20→22건/일

**교훈(꾹AI 에 이어 두 번째)**: 플랫폼 기본 URL 을 추정하지 말고 **목록 페이지의 실제 `<form>` 을 먼저 읽는다.** 남은 `scope-first` 2곳(놀장·시장을 방으로)도 같은 방식으로 재확인할 가치가 있다 — 다만 놀장은 색인 크롤에서 `/market/{id}` 안의 검색창이 시장 범위임을 실제로 봤다.

### 전일 색인 층 — 실시간이 닿지 않는 몰의 상품명을 미리 모아 둔다

야간 배치 **단계 F**(`backend/tools/index_nightly.js` → `online_product_index`)가 상품명·URL 만 걷고, `POST /api/online/search` 응답 끝에 `index` 층이 붙는다. 실시간 상태 목록에 섞지 않는다 — "어제 이 이름의 상품이 올라와 있었다"와 "지금 검색된다"는 다른 주장이다. 색인 대상 = 테이블에 행이 있는 몰 − 실시간 대상(한 몰이 두 층에서 다른 말을 하지 않게).

| 몰 | 방식 | 실측(2026-09-02) |
|---|---|---|
| 온누리 놀장 | sitemap 의 `/market/{id}` 14곳, 카드는 RSC 서버 렌더라 DOM 에서(썸네일+가격을 가진 카드만) | 293건 · 14페이지 · 111초 |
| 인어교주해적단 | `/store/onnuri` 화면이 스스로 받는 온누리 매장 158곳 → 매장 화면이 받는 메뉴 응답을 **가로채 읽는다**(직접 API 호출·토큰 재사용 없음) | 3,145건 · 159페이지 · 206초 |

- 예의: 호스트당 ≥1초, 페이지 상한 40/200, 이미지·폰트·분석 차단, 야간 1회 총 173페이지
- 가드: 수집 커버리지 50%·적재 시 기존 건수 대비 50% — 반쯤 걷힌 회차로 색인을 덮지 않는다. 한 몰이 실패하면 이전 색인이 유지되어 **항목 `collectedOn` 이 `asOf` 와 갈린다** — 화면의 `YYYY-MM-DD 수집분` 병기가 그 부분 실패를 알리는 유일한 통로다(지우지 말 것).
- 놀장은 상품별 고유 주소가 없어 `/market/{id}#상품명` 을 식별자로 쓴다 — 링크는 그 상품이 있는 시장 화면에 도착한다.
- 지니어스몰도 걷을 수 있음을 실측(전체상품 `총 1,541개`·`start=` 12개씩 129페이지·297초)했으나 실시간 대상이 되어 색인에서 뺐다.

### robots 8곳 (ADR-19)

사용자 결정은 "robots 무시하고 넣자". 2026-09-02 에는 하네스가 구현 위임을 두 차례 차단해 보류했고, **2026-09-03 사용자 재지시로 진행** — 1차 3곳(굿데이·인더마켓·팔도)과 재조사에서 열린 현대홈쇼핑을 편입해 **15곳**, 나머지 4곳은 6-10절의 판정(범위 오염 3·WAF 1)대로 비대상. 결과 절의 곳 수는 그 시점 기록이다.

### 결과

조회 대상 **11곳**, 확인하지 않는 곳 **11곳**(robots 8 / scope-first 2 / no-static-search 1), 색인 층 2곳. 제외 사유는 12곳 전수를 사전에 명시하고 테스트가 완전성을 고정한다 — 기본값으로 흘러가던 것이 "화면에서만 만들어져 읽을 수 없음 10곳"이라는 오표기의 원인이었다.

## 6-10. SPA 4곳 재조사 (2026-09-03)

ADR-19 로 robots.txt 가 대상 선정 기준에서 빠지면서, **robots 때문에 XHR 관찰조차 하지 않았던 4곳**(6-7절 표)을 처음으로 실제로 들여다봤다. 방법은 6-7·6-8절과 같다 — Playwright 로 화면 검색을 실행하며 document·XHR·fetch 를 전부 관찰하고, 질의어를 담은 요청을 `curl`(UA `Mozilla/5.0 (onnuri-guide-check)`)로 재현했다. 브라우저 위장·토큰 재사용·WAF 우회는 하지 않았다.

**결론: 1곳 편입 가능, 3곳 범위 오염으로 부적합.**

| 몰 | 질의어를 담은 요청 | 정적 재현 | 온누리 범위로 좁혀지나 | 결론 |
|---|---|---|---|---|
| 11번가 온누리마켓 | `GET search.11st.co.kr/pc/total-search?kwd=` | ○ | **✕ 11번가 전체 검색** | **범위 오염으로 부적합** |
| **현대홈쇼핑** | `GET hmall.com/md/api/cache?url=/api/hf/dp/v1/sect-mng/plansale-ancr-paging&sectId=3132118&…&searchTxt={q}` | **○** | **○ `sectId` 가 "현대홈쇼핑 온누리샵"** | **편입 가능** |

### 현대홈쇼핑 — 전용관 안에 자기 검색이 있었다

2. **응답이 캐시 프록시를 거친다.** 화면이 부르는 `/md/api/cache?url=…` 는 `__cache_metadata.status`(실측 `HIT_STALE`)를 붙여 준다. 캐시를 우회한 직접 경로 `https://www.hmall.com/api/hf/dp/v1/sect-mng/plansale-ancr-paging?…` 도 같은 파라미터로 동작한다(김치 2,780B). 화면이 보내는 것을 그대로 쓰는 원칙에 따르면 캐시 경로가 맞고, 신선도가 문제가 되면 직접 경로로 바꿀 수 있다.

카나리아 present 질의는 `김치`(1건)보다 **`쌀`(10건)이나 `세트`(20건)** 를 권한다 — 1건짜리는 그 상품 하나가 빠지면 다음 날 거짓 실패가 난다.

### 6-10-1. 전체 검색의 **상세 필터**로 온누리 범위가 잡힌다 (2026-09-03, 앞 절 정정)

사용자 질문("11번가와 롯데ON은 상세검색에 필터가 있지 않나?")으로 다시 봤다. **앞 절이 틀렸다** — 두 몰 다 검색 필터에 **온누리 전용 항목**이 있고, 전용관 밖에서 그것을 고르면 범위가 잡힌다. 앞 절은 전용관 **안**의 검색만 보고 "전체 검색뿐이니 범위 오염"으로 접었다. 필터를 열어 보지 않은 것이다.

| 몰 | 필터 항목 | 화면이 보내는 인자 | 결론 |
|---|---|---|---|
| **11번가** | 퀵필터 `온누리상품권` | `filters=ONNURI` | **범위 지정 가능 — 실시간 편입 후보** |
| **롯데ON** | 프로모션 필터 `온누리상품권 사용` | `u31=onnuri` | **범위 지정 가능하나 이용자 링크가 못 싣는다** |

#### 11번가 — `filters=ONNURI`

`GET apis.11st.co.kr/search/api/tab-filter?kwd={q}&tabId=TOTAL_SEARCH` 가 필터 그룹 전부를 준다: 속성(`attributes`) · 할인/적립(`benefits`) · 브랜드(`brandCd`, 500종) · 배송혜택(`benefits`) · 판매처(`sellerNos` — 백화점·대형몰·홈쇼핑·전문몰) · 결과 내 재검색 · 가격 · 상품 유형(`verticalType`) · **퀵필터(`filters`)** · 카테고리(`searchCategoryLarge`) · 정렬(`sortCd`) · 토글(`prdPrmtInfoList`).

퀵필터 첫 항목이 `{"name":"온누리상품권","code":"ONNURI","paramKey":"filters","count":810}` 다. 화면에서 실제로 눌러 확인한 인자가 `filters=ONNURI` 이고, **주소창에도 남는다.**

- 조회: `https://apis.11st.co.kr/search/api/tab?kwd={q}&tabId=TOTAL_SEARCH&filters=ONNURI`
- 이용자 링크: `https://search.11st.co.kr/pc/total-search?kwd={q}&tabId=TOTAL_SEARCH&filters=ONNURI` — 이 주소로 새로 열면 퀵필터가 **checked=true** 로 걸리고 API 도 `filters=ONNURI` 로 나간다(실측).

**범위가 기획전보다 정확하다.** 결과 상품의 상세 페이지에 `디지털온누리상품권 결제 가능` 배지와 안내문 `'디지털온누리상품권 결제 가능'으로 표기된 상품만 결제 가능합니다.` 가 붙어 있다 — 11번가가 스스로 표시한 **결제 가능 속성**이지 기획전 큐레이션이 아니다. 기획전(2210481) 상품은 테마 9개를 전수 받아 **고유 242건**인데, 그중 표본 4건을 상품명으로 ONNURI 검색하니 3건이 결과에 들어 있었다(나머지 1건은 질의어를 12자로 자른 탓에 0건). 즉 **필터 집합이 기획전을 포함하는 상위집합**이다.

| 질의 | 필터 없음 | `filters=ONNURI` | 응답 |
|---|---|---|---|
| 김치 | 278,339 | **938** | 842KB · 0.54초 |
| 로봇청소기 | — | **22** | 65.9KB |
| zzqqxyw12345 | — | **0** | 161.9KB · `isNr:true` |

규칙 재료:
- **없음-문구** `"groupName":"noSearchData"` — 있음 0회 / 없음 1회. 등급 B(구조적으로 함께 나올 수 없다). `"totalCount":0` 도 같은 성질이라 함께 둘 수 있다.
- **titlePattern** `"soldOut":(?:true|false),"title":"([^"]+)"` — 있음 106 / 없음 12(전부 추천 블록이라 질의어를 담지 않아 걸러진다). **앵커를 빼고 `"title"` 만 쓰면 안 된다** — SEO 제목 `김치 - 11번가 추천` 이 상품명 샘플로 나간다(6-5절 제목 에코 함정).
- **echoesQuery = true**, **noiseFloor = 9** — 없는 질의 4종(zzqqxyw12345·qqzzxxyy9988·zzzz9999·wjqhdxkalsem)에서 **전부 정확히 9회**였다(SEO 제목·설명·안내 문구). 이 값을 안 두면 `hits=9 ≥ likelyThreshold` 라 등급 B 문구가 있어도 `unclear` 로 빠진다.

**그럼에도 편입을 권하지 않는 이유 둘.**

1. **이용자 링크에 필터를 실을 수 없다.** 롯데ON 은 필터를 주소에 넣지 않는다 — 필터를 걸어도 주소창은 `…&sort=ranking` 그대로였고, `&u31=onnuri` 를 붙여 화면을 새로 열어도 **칩이 꺼져 있고 조회 요청에도 `u31` 이 없다**(실측). 링크는 몰 전체 검색이 되므로 **6-6절이 링크에서 뺀 이유가 그대로 남는다.** 조회는 온누리 범위인데 링크는 아닌 상태로 내보내면, 이용자는 "여기 있다더니 다른 게 나온다"를 겪는다.
2. **'없다'를 확정할 수단이 없다.** 결과가 없으면 롯데ON 은 `content-type: text/html` 에 **`content-length: 0`** 을 준다(없는 말 3종 전부 동일, 필터 유무 무관). 지금 `ProbeJudge` 는 API 몰 본문 하한을 60자로 두고 그 아래는 `unknown` 으로 접는다 — 빈 응답과 장애 응답을 구분할 수 없기 때문이다(6-7절). 그대로 넣으면 이 몰은 **없는 상품에 늘 `unknown`** 을 낸다. 쓰려면 "빈 본문 = 없음"을 타깃 단위로 선언하는 장치가 필요하고, 그건 6-7절이 일부러 세운 가드를 무르는 일이라 별도 판단이 필요하다.

titlePattern 후보는 `"pdName":\s*"([^"]+)"` 이고, 없음 응답이 비어 있어 echoesQuery 는 실측상 무의미하다(토큰 0).

#### 남는 교훈

두 몰 다 **한 번의 클릭 뒤에 답이 있었다.** 6-7절은 robots 를 보고 접었고, 6-10절은 전용관 화면만 보고 접었다. 전용관(범위)과 전체 검색(도구)을 각각 따로 본 것이 문제였다 — **전체 검색에 범위 필터가 있으면 둘이 만난다.** 남은 몰(공영쇼핑)에도 같은 질문을 다시 던져 볼 값이 있다.

#### 공영쇼핑도 같았다 — `benefit=trdit_mrkt_goods_yn`

같은 질문을 공영쇼핑에 던지니 여기도 있었다. `POST /search/ajaxSearchBenefit.do` 가 혜택 필터를 준다:

```
<gbn>trditmrk</gbn><nm>온누리</nm><val>trdit_mrkt_goods_yn</val><cnt>184</cnt>
```

화면에서 그 체크박스를 눌러 확인한 인자가 `benefit=trdit_mrkt_goods_yn` 이고, 기존 조회 본문에 그대로 얹힌다.

```
POST https://www.gongyoungshop.kr/search/ajaxSearchGoodsList.do
kwd={q}&reSrchFlag=false&pageNum=1&pageSize=40&sort=r&kwdType=0&benefit=trdit_mrkt_goods_yn&brandSort=cou&logFlag=true
```

| 질의 | 필터 없음 | `benefit=trdit_mrkt_goods_yn` | 응답 |
|---|---|---|---|
| 김치 | 2,733 | **184** | 10,688B · 0.12초 · `<prdNm>` 40 |
| 로봇청소기 | — | **0** | 1,136B · `<rsltYn>N</rsltYn>` |
| zzqqxyw12345 | — | **0** | 1,124B · `<rsltYn>N</rsltYn>` |

**앞 절의 "4/40" 판정은 착시였다.** 기획전(`ebtNo=4328`) 상품 표본 20건을 `POST /goods/getGoodsUnitInfo.do` 로 조회하니 **20건 전부 `trditMrktGoodsYn=Y`** 다. 필터 집합이 기획전을 포함하는 상위집합이고, 김치 상위 40건에서 겹친 것이 4건뿐이었던 것은 **정렬 상위만 봤기 때문**이다. 11번가·롯데ON 과 같은 구조다.

규칙 재료: 없음-문구 `<rsltYn>N</rsltYn>`(있음은 `Y`, 등급 B) · titlePattern `<prdNm>([^<]+)</prdNm>`(있음 40 / 없음 0) · echoesQuery **true**, noiseFloor **4**(`kwd`·`recKwd` 2회·`preKwd` — 없는 질의에서 4회 실측).

다만 **링크 제약은 롯데ON 과 같다.** `goodsSearch.do?kwd={q}&benefit=trdit_mrkt_goods_yn` 로 열어도 체크박스는 꺼져 있고 조회 요청의 `benefit=` 이 빈 값으로 나간다(실측). 데이터의 현재 `search_url_template` 은 몰 전체 검색이라 `{q}` 계약은 만족하지만 이용자는 필터 없는 목록을 본다.

또 하나 남는 불확실성: 이 필드의 이름은 `trdit_mrkt_goods_yn`(전통시장 상품 여부)이고 몰이 그것을 `온누리` 로 부른다. 11번가(`디지털온누리상품권 결제 가능` 배지)·롯데ON(`additionalFlagList type=onnuri`)처럼 **결제 가능 속성임을 상품 화면에서 확인하지는 못했다** — 상세 페이지의 `온누리` 8회가 전부 카드 컴포넌트의 Vue 템플릿이었다. 편입 전에 공영쇼핑 온누리 안내 문구를 한 번 더 확인할 값이 있다.

#### 6-10 결론 정정

| 몰 | 6-10(2026-09-03 오전) | **6-10-1 정정** |
|---|---|---|
| 11번가 온누리마켓 | 범위 오염으로 부적합 | **편입 가능** — `filters=ONNURI`, 링크도 범위를 싣는다 |
| 현대홈쇼핑 | 편입 가능 | 유지 — 전용관 `sectId` (링크가 질의어를 못 실음) |

**11번가만 조회·링크가 모두 온누리 범위로 잡힌다.** 나머지 셋은 조회는 범위 안이지만 이용자 링크가 그 범위를 재현하지 못한다 — 6-7절이 세운 "API 로 조회하면 데이터에 사람이 볼 검색 링크가 반드시 있어야 한다" 계약을 **'범위까지 같아야 하는가'로 한 겹 더 밀어붙일지**가 결정 사항이다.

## 6-10-2. 롯데ON — 전체 검색의 "온누리상품권 사용" 필터로 편입 (2026-09-03)

사용자 지적: "키워드로 검색한 다음 필터 카테고리 '상품' 안에 온누리상품권 사용 필터가 있는 것 같다." **맞았다.** 6-10 절이 롯데ON 을 범위 오염으로 접었던 것은 전용관 안의 검색만 보고 **전체 검색의 필터를 열어 보지 않았기 때문**이다(11번가·공영쇼핑과 같은 유형의 오판, 같은 날 세 번째).

좌측 필터 14개 그룹 중 **'상품' 그룹**에 `input[name=promotion][value=onnuri]` 체크박스가 있고, 누르면 화면이 `u31=onnuri` 를 얹은 요청 하나를 보낸다.

### 조회 (검증 CONFIRMED)

```
GET https://www.lotteon.com/csearch/search/search
    ?u2=0&u3=60&u16=ranking.desc&u31=onnuri&u37=true&u39=0
    &render=qapi&platform=pc&collection_id=9&mallId=1&q={q}
```

- **필수 헤더 0개** — UA·Accept·Referer·쿠키 없이 200. 브라우저가 받은 응답과 `cmp` 바이트 동일(114,923B).
- 실측: 로봇청소기 total 31 · 김치 1,166 · 다이슨 31 · 테슬라 7 · 아이폰 133. 0.52~0.62초, 12건 버스트 무차단.
- **범위 정확**: 김치 결과 1,960행을 꼬리 페이지까지 전수 확인해 **반례 0** — 전부 `additionalFlagList {"type":"onnuri"}` + `emblemInfo.emblemName="온누리"`. 무필터는 60건 중 15건뿐. 형제값 대조(`official` 146 · `new_pd` 15)로 `u31` 이 실제 작동함을 확인.

### '없음'을 확정하지 않는다 (검증 REFUTED — 등급 C)

온누리 0건이면 `{"itemList":[],"total":0}` 130바이트가 온다. 그러나 검증자가 **존재하지 않는 필터값 `u31=onnuriZZ`** 를 보내자 진짜 부재 응답과 **바이트·md5 완전 동일**(`c43847ceb4c3b53069316a6c72b0c6ef`)한 130B 가 돌아왔다. 130B 는 *온누리에 없다* 와 *필터가 깨졌다* 를 구분하지 못한다 — 롯데ON 이 파라미터를 바꾸는 날 **모든 질의가 조용히 '없음'** 이 된다.

0바이트 갈래는 더 나쁘다. 무의미어·`q` 누락·`q=` 빈 값이 전부 200 · `text/html` · length 0 · md5 `d41d8cd9…` 로 **완전히 같다**. 현실적인 다어절 질의 8건 중 2건(`다이슨 김치냉장고`·`샤넬 클래식백`)이 실제로 0바이트였다.

→ **온누리찬스와 같은 등급 C**: 없음-문구 없음 + `echoesQuery=true`(토큰 0 판정을 쓰지 않겠다는 정책 선언). 이 몰은 **never none** 이고 likely / unclear 만 낸다. `canDecideAbsent` 가 false 라 카나리아 absent 대조에서 빠지고, **present 기대치(김치 → likely + 샘플 ≥1)가 필터 파손을 잡는 유일한 장치**다.

### 이용자 링크에 필터를 실을 수 없다 (검증 REFUTED)

`promo=onnuri` 는 **모바일 UA 의 첫 화면에서만** 먹는다. 세 갈래로 무너진다.

| 경로 | 실측 |
|---|---|
| PC UA 로 그 URL 을 열면 | **302** — 필터가 증발해 무필터와 결과 동일 |
| 모바일에서 스크롤하면 | 첫 페이징부터 필터가 풀린다(김치 온누리 100% → 29%, 온누리 1,166건이 남아 있는데도). 페이징 요청 7건 전부에 필터 인자 없음 |
| 어느 경우든 | 화면이 필터가 켜졌다/꺼졌다를 **말하지 않는다** |

세 실패가 전부 **조용하다** — 이용자는 온누리 링크를 눌렀다고 믿은 채 결제 안 되는 상품을 본다. 그래서 `search_url_template` 을 비워 두고 링크는 `url`(상생스토어 단축주소)로 보낸다. 공영쇼핑과 같은 처리다. 주소창은 필터를 켜도 바뀌지 않으며, 해제할 때는 오히려 주소를 **다시 쓰면서 `sort=ranking` 만 지운다** — 앱이 주소를 고쳐 쓸 줄 알면서도 필터 상태는 결코 쓰지 않는다는 뜻이다.

### 남은 사실

조회 호스트가 몰 본체(`www.lotteon.com`, robots `User-agent: * / Disallow: /`)다 — 조회 호스트가 `apis.11st.co.kr` 로 갈라지는 11번가와 구조가 다르다. ADR-19 로 robots 는 대상 선정 기준에서 빠졌으나 이 차이는 기록해 둔다. 색인 층에서는 빠진다(실시간 대상은 색인하지 않는다).

**결과**: 조회 대상 **18곳**, 비대상 **4곳**(bot-blocked 1 · scope-first 2 · no-static-search 1). `scope-mixed` 는 붙는 몰이 없어져 사라진 네 번째 사유가 된다.
