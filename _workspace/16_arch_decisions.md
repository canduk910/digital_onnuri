# 16. 아키텍처 결정 기록 (ADR)

경량 ADR 대장 — 형식·운영 규칙은 `.claude/skills/app-architecture/SKILL.md`. 새 결정은 아래에 누적하고, 뒤집을 때는 새 ADR로 "ADR-x를 대체"를 명시한다.

## ADR-1: 검색만 서버로 이관, 나머지는 정적 유지 (2026-08-08)
- 맥락: 가맹점 66k건(20MB+)을 클라이언트가 통째로 받아 필터 — 전송·메모리 부담. 반면 가이드 콘텐츠·온라인 목록은 KB급.
- 결정: 가맹점 검색·집계만 Spring+Postgres API로 이관. 페이지·온라인 목록은 정적 JSON 유지.
- 근거: 서버화의 이득(전송량·페이징)은 MB급 데이터에만 있다. 전면 서버화(SSR) 대안은 정적 호스팅(GitHub Pages)의 무비용·무장애 이점을 버려 기각.
- 결과·롤백: backend/ 신설(feat 브랜치). 롤백 = 프론트 dataMode를 json으로.

## ADR-2: 이중 데이터소스 dataMode(auto/api/json) + 폴백 대칭 불변식 (2026-08-09)
- 맥락: 백엔드 배포 전/장애 시에도 라이브가 죽으면 안 됨.
- 결정: config.js dataMode — auto는 API 프로브 실패 시 JSON 폴백. 서버 필터 규칙 ≡ 프론트 JSON 계산 규칙을 1급 불변식으로.
- 근거: 프록시·캐시 레이어 대안보다 단순하고, 정적 사이트가 최후 보루로 남는다. 대가: 규칙을 항상 양쪽에 구현(경계면 검증 필수 — dev-testing).
- 결과·롤백: 폴백 순간에도 동일 카운트. 스위치 한 줄로 모드 전환 가능.

## ADR-3: index.html은 번들 유지 + 빌더 재생성 (2026-08-06, 지속)
- 맥락: index는 4MB 자가해제 번들(외부 산출물). 직접 수정 시 D-F1(이스케이프 깨짐 → 백지)로 전체 붕괴.
- 결정: 직접 수정 금지. build_index.py가 .bak 원본에서 치환 스텝으로 재생성, "리터럴 </ = 0" 불변 검증.
- 근거: 번들을 일반 페이지로 재작성하는 대안은 축적된 DC 로직 재구현 비용·회귀 위험이 커 기각. 대가: 셸 변경도 빌더 스텝으로 우회(FOUC 방어 등).

## ADR-7: 지도범위(bounds) 검색은 전 지역 + region 생략 (2026-08-10)
- 맥락: bounds 검색이 시도 탭에 종속되면 지도 위치와 탭이 어긋날 때 0곳.
- 결정: bounds 활성 시 시도 무관 전 지역 검색 — API는 region 파라미터 생략, JSON은 4파일 합본. 지도 idle 시 자동 재검색(수동 재적용 제거).
- 근거: "지도에 보이는 것을 검색"이라는 사용자 멘탈 모델에 지역 개념이 없다. 대가: JSON 모드 첫 실행 시 전 파일 로드(로딩 안내로 완화).
- 결과·롤백: 서버는 hasBounds 분기(Specs). 롤백 = regionParams에 region 복원.
- **표류와 복원(2026-09-05)**: 2026-08-12 "뷰포트 자동 지도" 커밋이 `bounds` 를 **추가 AND** 로 바꾸며 이 결정의 핵심(지역 대체)을 폐기했는데 **이 ADR 을 갱신하지 않았다.** 그래서 24일 동안 문서는 "region 생략", 코드는 `region AND bounds` 였다 — 다음 사람이 ADR 을 정본으로 믿고 코드를 "고치면" 검색 의미가 바뀌는, 위험 방향이 나쁜 어긋남이었다(2026-09-05 백로그 E1 이 적발). 사용자 결정으로 **코드를 이 ADR 쪽으로 되돌렸다** — "보이는 곳을 검색한다"는 멘탈 모델이 여전히 옳다는 판단이다. 실측: 시도 탭 '서울'인 채 지도를 수원 팔달구로 옮기면 종전 **0곳** → 지금 **경기 76곳**. 대신 활성으로 보이는 지역 컨트롤이 결과에 걸리지 않으므로 **그 자리에서 그 사실을 말한다**(`#regionOff` — "지도 범위로 보는 중 — 지역 선택은 잠시 적용되지 않습니다", 셀렉트는 흐림). 화면 표시도 "지도 범위 · **전 지역** N곳"으로 — 시도 이름을 적으면 이제 그것이 거짓이다. 정적 계약 3건으로 고정(변조 3종 EXIT=1). AND 시절의 근거였던 "지도는 늘 뷰포트를 그린다"는 여전히 참이고, 바뀐 것은 **목록**의 스코프다.

## ADR-12: 챗봇 — RAG(pgvector) + 서버 도구 루프 + 플로팅 위젯 (2026-08-11)

## ADR-17: 온라인 상품 실시간 조회 — "없음 확정 + 근거 제시" 6곳 (2026-08-31)
- 맥락: 온라인 키워드 검색이 플랫폼 단위 태그를 `indexOf` 단일 부분문자열로 훑어, "삼성전자 비스포크 로봇청소기"처럼 공백이 든 상품명은 **무조건 0곳**이었다. 태그를 35종까지 세분해도(2026-08-27) "이 몰이 가전을 판다"까지만 알 뿐 "그 상품이 있느냐"에 답하지 못한다. 사용자 요청 — 실시간 병렬 조회로 정밀도를 올릴 수 있는가.
- 결정: **ADR-6이 남긴 하이브리드 롤백 경로를 발동한다.** 이용자가 버튼을 누르면 **6곳**을 병렬 조회해 취합하는 `POST /api/online/search` 신설. 단 **"있음"이라는 판정 상태를 만들지 않는다** — `none`(없음 확정) / `likely`(관련 상품이 검색됨, 상품명 예시 첨부) / `unclear` / `unknown` / `not-probed`. 규칙(`ProbeTargets`)은 Java 상수, 몰별 검색 링크는 DB+JSON. 상세는 `_workspace/19_online_probe.md`.
- 근거: 2026-08-31 실측. ①대상 선정 — `app` 컨테이너가 `21-jre`라 브라우저가 없어 **정적 HTTP 응답에 결과가 실리는 몰만** 가능하다. 22곳 중 8곳이 되고, 그중 2곳(온누리굿데이·인더마켓)은 **robots.txt가 `Disallow: /`** 라 제외해 6곳. 브랜드 178종 중 146종(82%) 커버, 병렬 5.2초. ②판정 — 응답에 검색어가 있다고 상품이 있는 게 아니다. 온누리굿데이는 `"비스포크 로봇청소기 검색결과"` **제목 에코**만으로 토큰 3종이 각 1회 잡혔고, 온누리찬스는 없는 키워드에도 노이즈 2가 나오며, `로보락 큐레보`는 **호환 리필 물걸레**를 물어온다. 반면 없는 키워드로 조회하면 6곳 중 4곳이 명시적 "결과 없음" 문구를 낸다. **"0이면 없다"는 신뢰할 수 있고 "0이 아니면 있다"는 신뢰할 수 없다** — 이 비대칭이 설계의 축이다. ③없음-문구는 3등급으로 나눈다 — 검색어 바인딩형(A, 단독 확정) / 비의존형(B, 토큰 대조 병행) / 사전 없음(C). `onnuri-market`은 **약관의 "…없습니다"만 검출**되어 페이지 전체 매칭 시 항상 "없음"이 되므로 등급 C로 비워 둔다. ④상품명 추출은 몰별 정규식이 필요해 ADR-6이 우려한 "구조 변경에 취약"에 해당하므로 **판정 경로 밖**에 둔다 — 깨져도 "근거 없는 `likely`"로 품질만 떨어지고 오답이 되지 않는다.
- 기각한 대안: ①히트 카운트 임계만으로 있음/없음 — 실측 반증(에코 1·1·1 vs 실상품 29), 경계가 몰마다 다름 ②상품 카드 CSS 셀렉터를 판정 근거로 — ADR-6이 기각한 취약성을 판정 필수 경로에 들임 ③없음-문구를 페이지 전체 매칭 — 온누리마켓 약관 오탐 ④규칙을 DB에 — 파서와 원자성이 깨져 "규칙 절반만 바뀐 상태" 발생, CI 미검증, 실측 근거 주석 자리 없음 ⑤런타임 robots.txt 조회 — 아웃바운드 2배로 부담 억제에 역행(배치 1일 1회로 대체) ⑥타이핑 자동 조회 — ADR-16의 부담 억제 근거 위반, 오타에서도 발동 ⑦카나리아 실패 시 자동 비활성화 — 조용한 축소(ADR-16이 자동 반영을 기각한 논리와 동일) ⑧Playwright로 나머지 14곳 — app 컨테이너에 브라우저 없음, 2 vCPU 부적합.
- 결과·롤백: 이용자 경로 아웃바운드는 버튼 트리거·캐시(TTL 60분)·몰당 동시 1건·몰당 분6일600·IP당 분5일100·전역 동시 12로 묶는다. 깨짐은 야간 배치 **단계 E**(셀프테스트 엔드포인트를 배치가 curl, 몰당 2질의 = 12요청/일)가 탐지하되 자동 수정하지 않는다. 롤백 = `app.online.probe.enabled=false` — 끄면 전 항목이 `not-probed/disabled`로 나가고 화면은 22곳 검색 링크를 그대로 제공한다(기능이 조용히 사라지지 않는다). 한계: **6곳 안에서만 "없다"가 참이고**, 나머지 16곳은 "확인하지 않았다"로 표시하며 링크를 준다.
- 구현 중 정정(2026-08-31): ①`titlePattern`을 1단계에서 **선언만 하고 6곳 모두 null로** 둔 채 넘어가, 화면에 카운트만 남고 근거가 하나도 없었다 — 5단계 렌더 검증에서 발견해 6곳 마크업을 실측해 채웠다. 이 필드가 비면 카나리아의 `present` 기대치(샘플 ≥1)도 성립하지 않는다. ②`mallWide`를 `likelyCount`에서 뺀 것까지는 맞았으나 안내 문구에서도 사라져 "6곳을 확인했습니다"라면서 5곳만 설명하는 문장이 나왔다 — 확인한 곳 수와 설명한 곳 수가 어긋난다. ③카나리아 인증은 `?key=`가 아니라 `X-Admin-Key` 헤더로 한다 — 배치의 명령줄은 cron 로그·프로세스 목록에 남는다. ④robots 감시 도메인을 배치 상수에 손으로 적었다가 굿데이를 엉뚱한 도메인으로 지정했고 **그 도메인이 마침 `Disallow: /`라 기대치와 맞아 통과했다** → 도메인은 `data/online_platforms.json`에서 뽑는다. ⑤배포 후 라이브에서 `다이슨 청소기` 조회 시 온누리공공몰 샘플 20건이 **전부 '청소기'만 맞고 다이슨은 0건**이었다 — "관련 상품이 검색됨"과 함께 다이슨 아닌 이름을 근거로 내밀어 "공공몰에 다이슨이 있다"로 읽힌다. 샘플을 질의 낱말 포함 수로 정렬하고 `samplePartial` 플래그를 계약에 더해 화면이 "검색어의 일부 낱말만 맞는 결과"라고 말하게 했다. **판정은 낮추지 않았다** — 낮추면 titlePattern 없는 몰에서 판정이 샘플에 끌려다녀 "샘플은 판정 경로 밖" 원칙이 무너진다. ⑥2026-09-01 조회 대상 **6곳 → 7곳**(꾹AI온누리몰). 4단계에서 "`?keyword=` 로 검색된다"고 보고 링크만 줬는데 재조사해 보니 **그 URL 은 검색이 실행조차 되지 않았고**(있는 말·없는 말의 상품 링크 20개가 동일, 차이는 로그인 return URL 한 줄), 당시 센 "김치 7회"는 카테고리 메뉴의 '김치·반찬'이었다 — 1단계에서 설계 축으로 세운 "에코를 상품으로 오인하지 않는다"를 4단계에서 스스로 어긴 것이고, 그 결과 **잘못된 링크가 라이브에 나가 있었다.** 실제 폼을 제출해 `keytype` 이 필수임을 찾아 URL 을 고치고 규칙을 실측해 승격했다. 이 과정에서 `echoesQuery` 선언(true)과 실측(false)의 차이를 **카나리아가 잡아냈다** — 6단계에 넣은 장치가 첫날 값을 했다. ⑦2026-09-02 조회 대상 **7곳 → 10곳**. "화면에서 결과가 만들어지는" 몰도 조회 가능하게 해 달라는 요청에, **브라우저를 들이지 않고** 그 화면이 부르는 **내부 검색 API 를 직접 호출**해 풀었다(공식 화면이 보내는 것과 같은 요청이라 제약을 우회한 것이 아니다). robots 가 4곳(11번가·현대홈쇼핑 전면차단, 사이소·공영쇼핑 `/api`·`/search` 금지)을 먼저 걸러냈고, 남은 7곳 중 2곳(현대이지웰·온누리5일장)에서 API 를 찾았다. 구조 확장 2건 — `{qq}`(이중 인코딩)·`formBody`(form POST). **판정 엔진은 고치지 않았다**(정규식 기반이라 JSON 도 동작). 다만 "본문 500자 미만 = unknown" 가드가 HTML 전제라 API 의 짧은 '없음' 응답(316자)을 뭉갰고 **카나리아가 잡아** API 몰만 60자로 낮췄다. 그리고 `searchUrlFor` 가 조회 URL 을 이용자 링크로 쓰고 있어 **JSON 이 링크로 나갈 뻔한 것**을 데이터 우선으로 뒤집었다. 재시도에서 온누리쇼핑도 편입했다 — 검색 UI 가 클릭으로 열려 폼을 못 찾았을 뿐 결과는 서버가 렌더한다(`/search?searchWrd=`). 남은 4곳은 검색 기능이 없거나(지니어스몰·인어교주해적단) 주소·매장 선택이 선행된다(시장을 방으로·놀장).

## ADR-18: 온라인 상품명 **전일 색인 층** + 제외 사유 사전 전수화 (2026-09-02)
- 맥락: 실시간 조회 10곳 이후 남은 12곳을 더 열 방법을 전수 검토했다(`_workspace/20_probe_expansion_analysis.md`). 12곳 중 **8곳은 robots.txt** 가 막고(굿데이·인더마켓·팔도·11번가·현대홈쇼핑·롯데ON·사이소·공영쇼핑), 1곳은 검색 기능이 없고(지니어스몰), 2곳은 시장·주소 선택이 먼저이며(놀장·시장을 방으로), 1곳은 검색 API 가 인증을 요구한다(인어교주해적단). **브라우저를 들여도 실시간으로 열리는 곳은 1곳**이다 — 병목은 렌더링이 아니라 허락과 범위다. 그리고 화면은 이 12곳을 "화면에서만 만들어져 읽을 수 없음 10곳"으로 잘못 말하고 있었다 — `EXCLUSION` 사전이 2곳만 적고 나머지를 기본값으로 흘렸기 때문.
- 결정: ①**robots 가 막은 8곳은 보류**(사용자 결정 2026-09-02 — 허가 없이는 건드리지 않는다). ②`EXCLUSION` 을 12곳 전수 명시로 바꾸고 사유를 4종으로(`robots-blocked` 8 / `no-search-feature` 1 / `scope-first` 2 / `no-static-search` 1). 데이터의 비대상 몰이 사전에 없으면 테스트 실패 — 기본값이 오표기의 원인이었다. ③**전일 색인 층** 신설 — 야간 배치가 Playwright 로 지니어스몰(카테고리 목록)·놀장(sitemap 의 시장 30여 곳)·인어교주해적단(온누리 매장 목록 → 매장별 메뉴, 브라우저가 부르는 JSON 응답을 가로채 읽는다)의 **상품명·URL 만** 수집해 `online_product_index` 에 저장하고, `POST /api/online/search` 응답 끝에 `index` 층(별도 record)을 덧붙인다. 실시간 상태 목록(none/likely/…)에 `indexed` 를 **넣지 않는다** — "어제 이 이름의 상품이 올라와 있었다"와 "지금 검색된다"는 다른 주장이고, 섞으면 문구가 거짓이 된다.
- 계약: `OnlineSearchResult` 마지막 필드 `IndexLayer index`(null 금지, 비면 platformCount 0·notice null·items 빈 목록). `IndexLayer(asOf=포함 몰의 min(collectedOn), platformCount, foundCount, notice, items)`. `IndexHit(platformId, name, matchCount, sampleTitles≤3, samplePartial, searchUrl, collectedOn)`. 낱말 분리는 `ProbeQuery` 와 같은 규칙(서버 단일 출처). 실시간 조회 대상(`ProbeTargets.ids()`)은 색인 층에서 제외 — 한 몰이 두 층에서 다른 말을 하지 않게. 배치 적재 가드: 몰별 새 건수가 기존의 50% 미만이면 유지(반쯤 걷힌 회차로 색인을 덮지 않는다 — 단계 A ±20% 가드와 같은 논리).
- 기각한 대안: ①웜 풀 헤드리스 사이드카로 실시간 — 여는 곳이 1곳(인어교주)이라 2 vCPU 상주 프로세스를 정당화 못 함. 색인 배치가 이미 브라우저를 쓰므로 필요하면 그 위에 얹는다(보류) ②WAF 우회·앱 API 역공학·번들 토큰 재사용·robots 무시 — 코스콤 이름의 공개 가이드가 질 위험이 열리는 곳 수보다 크다 ③원격 렌더링 서비스 — 질의어가 제3자로 나가고 A4 로 충분 ④색인을 실시간 status 로 통합 — 위 결정 ③의 이유 ⑤별도 엔드포인트 — 버튼 한 번에 두 층이 함께 나와야 하고 문구 권한(notice)이 둘로 갈리면 카운트가 어긋난다.
- 결과·롤백: 아웃바운드는 야간 1회(몰 3곳 · 페이지 100~150건 · 호스트당 1req/s). robots 감시(단계 E)에 3곳을 추가해 정책 변화를 매일 본다. 롤백 = 단계 F 스킵(`--skip-index`) + 테이블 비우기 → `index` 층이 비어 화면 블록이 사라진다(실시간 층 무영향). 후속: 허가가 오는 robots 몰은 기존 규칙으로 즉시 편입, 네이버쇼핑검색 API 입점 확인은 별건.
- 구현 중 정정(2026-09-02): 크롤러 레시피 실측 중 **지니어스몰에 정적 검색이 실존**함이 드러났다 — `GET /product/product.html?search={q}`(로봇청소기 12건·50.9KB / 없는 말 0건·29.8KB, `총 <i>N</i>개`). 20절 5절이 시험한 4변형은 파라미터 이름을 `keyword`·`search_text` 로 추정했고 실제 폼의 `name="search"` 를 놓쳤다 — "검색 input 0개"(6-8절)는 홈에만 폼이 없다는 관찰이었고, 폼은 상품 목록 페이지 안에 있었다. **교훈: 플랫폼 기본 URL 추정보다 목록 페이지의 실제 `<form>` 을 먼저 본다**(6-5절 꾹AI와 같은 유형). robots 허용(`/product/`)이라 **실시간 조회 11번째 대상으로 승격**, `no-search-feature` 사유는 붙는 몰이 없어 만들지 않는다(사유 3종). 색인 층 대상은 놀장·인어교주 2곳.

## ADR-19: robots.txt 를 조회 대상 선정 기준에서 제외 (2026-09-02) — ADR-17 ①·ADR-18 ① 을 대체
- 맥락: ADR-17 은 robots `Disallow` 몰을 기술적으로 되더라도 조회하지 않았고(굿데이·인더마켓), 이후 조사에서 robots 가 8곳을 걸러냈다. 사용자 결정(2026-09-02): "robots.txt 는 무시하자." 근거로 든 "구글·클로드도 무시한다"는 사실과 다르다(Googlebot·Anthropic 크롤러는 robots 를 따른다) — 이 점을 알린 뒤에도 결정이 유지됐다.
- 결정: robots.txt 는 **조회 대상 선정 기준에서 뺀다.** 대상 선정은 ①정적 HTTP(화면 또는 내부 API)로 결과가 실리는가 ②온누리 범위로 좁힐 수 있는가(기획전 딥링크의 범위 오염 금지) ③판정 재료(없음-문구·titlePattern)가 실측되는가 — 세 가지만 본다. **WAF 가 봇을 능동 차단하는 몰(사이소)은 여전히 제외** — 그것을 넘으려면 브라우저 위장이 필요하고, 그건 "요청을 안 받겠다"는 사이트를 속이는 일이라 robots 를 안 따르는 것과 성격이 다르다. 부담 억제(버튼 트리거·캐시·몰당 분6일600·IP당 분5일100)는 그대로 — robots 를 안 따르는 대신 실제 부담을 낮게 유지하는 것이 이 결정의 균형점이다. `Crawl-delay`(11번가 1초·롯데ON 3초)는 몰당 동시 1건 제한이 이미 충족한다.
- 근거·리스크: 국내 판례(야놀자·여기어때 형사 무죄·민사 배상, 잡코리아·사람인 크롤링 금지)는 **대량·상업적 복제**가 쟁점이었고, 이 조회는 이용자 1회 질의당 검색 페이지 1건을 읽어 링크로 돌려보내는 저부하·비축적 구조다. 그래도 접근 거부 의사(robots)를 알고 넘는 것이므로 운영사 항의 시 즉시 끄는 경로(킬스위치·몰 단위 제거)를 유지한다. 색인 층(ADR-18)의 야간 크롤은 robots 무시 대상에 **넣지 않는다** — 그쪽은 축적형이라 판례가 겨눈 유형에 가깝다.
- 결과: 즉시 편입 후보 3곳(굿데이·인더마켓·팔도 — 정적 실측 완료) + 재조사 4곳(11번가·현대홈쇼핑·롯데ON·공영쇼핑 — robots 때문에 XHR 관찰을 하지 않았던 곳). 제외 사유 `robots-blocked` 는 사라지고 남는 비대상은 실제 사유(SPA·범위·인증·WAF)로 적는다. 단계 E robots 감시는 정책 변화 기록용으로 유지. 롤백 = 해당 타깃 제거 + ADR-18 ① 복원.
- 상태(2026-09-02): **구현 보류.** robots 차단 몰을 조회 대상에 넣으라는 위임을 Claude Code 하네스의 자동 승인 분류기가 차단했다(사이트가 명시적으로 거부한 자동 접근을 지시하는 내용이라는 판정). 우회하지 않고 사용자에게 돌려보냈다 — 사용자가 권한 규칙을 추가하거나 직접 반영하기 전까지 ADR-18 ①(robots 8곳 보류)이 유효하다.
- 상태 갱신(2026-09-02, 같은 날): 하네스 차단과 리스크를 설명한 뒤 **사용자가 재확인**("robots.txt 에서 명시적으로 거부했어도 대상에 넣고 싶어") → **진행.** 1차: 정적 실측이 끝난 3곳(굿데이·인더마켓·팔도) 편입. 2차: robots 때문에 XHR 관찰을 하지 않았던 4곳(11번가·현대홈쇼핑·롯데ON·공영쇼핑) 재조사 후 되는 곳 편입. 사이소(WAF)는 제외 유지.
- 상태(2026-09-02, 재시도): 사용자 재확인 후 위임을 다시 보냈으나 **하네스 분류기가 재차 차단.** 이 세션에서는 구현하지 않는다 — 우회하지 않고 사용자에게 돌려보냄. 사용자가 다른 권한 모드에서 직접 반영하거나 세션 설정을 바꾸기 전까지 ADR-18 ①(robots 8곳 보류)이 유효하다. 1차 편입 재료는 갖춰져 있다: 굿데이·인더마켓(`pn=product.search.list&search_word={q}`, 1절 31/0·33/0), 팔도(`/goods/search.aspx?q={q}`, 6-6절 60/2) — 각각 없음-문구·titlePattern·echoesQuery 실측 + 픽스처 2개 + EXCLUSION 에서 제거 + 카나리아 자동 파생.

## ADR-20: 온라인 사용처 페이지를 「상품 실시간 검색」·「몰 둘러보기」 두 탭으로 분리 (2026-09-02)

- 2차 결과(2026-09-03, 19절 6-10): SPA 4곳 중 **현대홈쇼핑만 편입**(전용관 `sectId=3132118` 범위 검색 API, `"itemList":[]` 등급 B, `"slitmNm"` titlePattern, echoesQuery true, 0.07초 — 6-7절이 robots 만 보고 접었을 때 전용관 자체 검색창을 놓쳤다). 11번가·롯데ON·공영쇼핑은 검색은 정적으로 되지만 **결과가 몰 전체라 범위 오염** → 새 사유 `scope-mixed`(그동안 `no-static-search` 로 적혀 있던 것은 사실과 달랐다). 파생 결정 3건: ①현대홈쇼핑 전용관은 URL 질의를 무시해 이용자 링크에 `{q}` 를 실을 수 없다 → API 몰의 링크 계약을 "`{q}` 필수"에서 "사람이 볼 링크 필수(전용관 자체 검색창)"로 완화 ②공영쇼핑 몰 전체 검색 링크(`/search/goodsSearch.do?kwd=`)는 김치 40건 중 온누리 기획전 450개에 드는 것이 4건뿐이라 **제거**(6-6절 롯데ON 과 같은 이유), dataVersion 2026-09-03 ③세 곳의 기획전·스토어 상품명은 정적 JSON 으로 받히므로 **색인 층(ADR-18) 대상을 2→5곳**으로 — 실시간 검색은 못 해도 "그 몰의 온누리 범위 안에 이 이름이 있었다"는 답할 수 있다. 색인 크롤은 robots 를 따르되 이 셋의 `Crawl-delay`(11번가 1초·롯데ON 3초)를 지킨다.
- 3차 정정(2026-09-03, 19절 6-10-1): 사용자 지적("11번가·롯데ON 은 상세검색에 필터가 있지 않나")이 맞았다 — 세 몰 모두 **전체 검색의 상세 필터에 온누리 전용 항목**이 있다(11번가 `filters=ONNURI` 결제 가능 속성 · 공영쇼핑 `benefit=trdit_mrkt_goods_yn` 기획전 표본 20/20 포함 · 롯데ON `u31=onnuri`). 2차 조사는 전용관 **안의** 검색만 보고 전체 검색의 필터를 열어 보지 않았다 — 전용관(범위)과 전체 검색(도구)을 따로 본 것. **11번가·공영쇼핑 편입 → 17곳**(11번가는 링크에도 필터가 실려 조회·링크 모두 범위 일치, 공영은 링크가 기획전 홈). **롯데ON 은 보류** — ①링크가 필터를 못 싣는다(주소에 넣어도 칩이 꺼짐) ②결과 없음이 `content-length: 0` 이라 '없다'를 확정하려면 "빈 본문 = 없음"을 타깃 단위로 열어야 하는데, 그건 오류 페이지를 걸러 내는 가드를 무르는 일이라 하지 않는다(있는 것을 없다고 말하는 방향의 위험). 색인 대상은 3곳(놀장·인어교주·롯데ON). 비대상 5곳(bot-blocked 1 / scope-first 2 / scope-mixed 1 / no-static-search 1). 교훈: **"전용관 안에 검색이 없다"는 "범위 검색이 불가능하다"가 아니다** — 전체 검색의 필터 목록을 먼저 열거한다.
- 카나리아 부작용 적발(2026-09-03): 굿데이 없음 응답의 **인기 검색어 블록(`og_pop_item`)과 자동완성 배열(`ogAC`)에 카나리아의 없는 말 `zzqqxyw12345` 가 올라가 있었다** — 매일 같은 말을 보내니 그 몰이 그것을 인기 검색어로 집계해 **상대 사이트 이용자에게 노출**된 것. 같은 이유로 stripEcho 가 걷지 않는 본문에 질의어가 남아 카나리아가 "echoesQuery 선언(false)≠실측(true)"을 냈다(카나리아 기준 정정 뒤에도 남은 1건). 조치: absent 질의를 회차마다 무작위 생성(`zq`+소문자 8자 — 어느 몰의 인기·최근 검색어에도 쌓이지 않게). 굿데이 `echoesQuery` 는 **false 유지** — 무작위 질의로 부르면 인기검색어·자동완성·본문 히트가 전부 0(실측)이라 원인은 몰의 성질이 아니라 우리의 반복이었고, 우리가 만든 부작용을 근거로 그 몰의 '없다' 확정 수단을 버리지 않는다(backend 반박 수용). 인더마켓은 인기검색어 블록 자체가 없다. 남은 것: 굿데이 인기검색어의 `zzqqxyw12345` 는 그 몰의 집계가 밀어낼 때까지 남는다. 교훈: **없는 말도 반복하면 흔적이 된다** — 카나리아는 상대에게 보이지 않아야 한다.
- **후속 과제(2026-09-03 확정, 다음 라운드)** — ADR-19 의 균형점("정책이 강해지면 즉시 끈다")이 걸린 **robots 감시가 제 구실을 못 하고 있다.** 네 갈래로 어긋나 있고 넷을 한 번에 고쳐야 한다. ①**관측점이 틀렸다** — `_robots_targets()` 가 `search_url_template or url`(이용자 링크 호스트)로 대상을 정하는데 우리가 두드리는 곳은 다르다(11번가 감시 `search.11st.co.kr` ↔ 조회 `apis.11st.co.kr`, 롯데ON 감시 `s.lotteon.com` 301 루프 ↔ 조회 `www.lotteon.com`). 호스트의 출처는 `ProbeTargets` 하나여야 하고, 손으로 적으면 2026-08-31 굿데이 도메인 오기가 재발한다 → 셀프테스트 응답에 조회 호스트를 실어 배치가 받는다. ②**색인 2곳(놀장·인어교주)은 `ProbeTargets` 에 없어** 앱 응답만으로는 관측 밖이 된다 — `index_nightly.js` 의 `RECIPES.hosts` 를 배치가 뽑아 합친다(양쪽 다 손으로 안 적는다). ③**키를 id 가 아니라 호스트로** — robots.txt 는 호스트 단위 파일이고 한 몰이 두 호스트를 쓰거나(인어교주) 두 몰이 한 호스트를 나눠 쓰면 id 키가 어긋난다. ④**판정이 절반만 맞다** — 스캐너가 `Disallow: /` 한 줄만 봐서 11번가처럼 `Disallow: /` + `Allow: /plan/front/` 인 곳을 전면 차단으로 오독한다. 물어야 할 질문은 "전면 차단인가"가 아니라 **"우리가 두드리는 그 경로가 아직 허용되는가"** 다 — UA 그룹 선택 + 최장일치 Allow/Disallow 가 필요하다. 호스트만 고치면 "관측점은 맞는데 판정이 틀린" 상태가 남는다. 덧붙여 기준선 상수 `ROBOTS_BLOCKED_AT_SURVEY` 도 같은 병이다(편입 때 넣는 걸 잊으면 조용히 거짓 통과) → **어제 리포트와 비교**하는 쪽으로 바꾸면 상수가 없어진다(`_prev_canary` 가 응답 길이에 이미 쓰는 패턴). 그리고 `_robots_scan()` 이 셀프테스트 성공 경로 안에 있어 **관리자 키가 없거나 킬스위치가 꺼지면 robots 를 아예 안 본다** — 조회가 꺼져 있어도 robots 는 보도록 떼어 놓는다.
- 상태 갱신(2026-09-03, 4차 정정 — 앞선 "롯데ON 보류·색인 3곳·비대상 5곳" 기록을 대체): 사용자가 **전체 검색의 필터**를 짚어 주어 롯데ON 도 열렸다("상품" 그룹의 `온누리상품권 사용` → `u31=onnuri`, 19절 6-10-2). **조회 대상 18곳 / 비대상 4곳**(bot-blocked 1 · scope-first 2 · no-static-search 1) / **색인 2곳**(놀장·인어교주). `EX_SCOPE_MIXED` 는 붙는 몰이 없어져 상수째 삭제 — 사라진 네 번째 사유다. 보류 사유 두 가지는 이렇게 처리했다: ①**'없다'를 말하지 않는다** — 온누리 0건 응답(130B)이 **존재하지 않는 필터값 응답과 바이트·md5 동일**이라 부재와 파손을 구분할 수 없다. 찬스와 같은 등급 C(없음-문구 없음 + `echoesQuery=true` 정책 선언)로 **never none**, likely/unclear 만 낸다(dev-qa 가 `ProbeJudge` 의 NONE 반환 3지점이 모두 닫힘을 코드로 확정). 이 몰은 카나리아 absent 대조에서 빠지므로 **present 한 건이 유일한 감시 지점**이다 ②**링크에 필터를 실을 수 없다** — PC 는 302 로 증발하고 모바일도 첫 스크롤에 풀린다(김치 온누리 100%→29%). 배지로 단서를 붙이는 대신 **행선지를 상생스토어로 바꿔** 풀었다(공영쇼핑 기획전 홈과 같은 처리). **이 구분이 중요하다** — "조회 범위가 오염되면 배지를 붙이면 된다"로 읽으면 다음에 온누리로 못 사는 상품을 보여 주는 쪽을 고르게 된다. `scope-mixed` 가 지워진 이유도 위험을 감수해서가 아니라 **범위를 좁힐 방법을 찾아서**다. 조회 호스트가 몰 본체(`www.lotteon.com`, `Disallow: /`)라는 점은 기록해 둔다 — 11번가는 `apis.11st.co.kr` 로 갈라진다.

## ADR-21: robots 감시를 "우리가 두드리는 경로가 허용되는가"로 바꾼다 (2026-09-03)
- 맥락: ADR-19 가 robots 를 조회 대상 선정 기준에서 빼면서 내건 균형점이 "정책이 강해지거나 항의가 오면 즉시 끈다"였고, 그 관측 수단이 야간 배치 단계 E 의 robots 감시다. 그런데 그 감시가 **두 군데 어긋나 있었다**. ①**관측점** — 대상 호스트를 `search_url_template or url`(이용자 링크 호스트)에서 뽑아, 우리가 실제로 두드리는 곳을 보지 않았다(11번가 감시 `search.11st.co.kr` ↔ 조회 `apis.11st.co.kr` / 5일장 감시 본몰 ↔ 조회 `api.samaint.co.kr` / 롯데ON 감시 단축주소 301 루프 ↔ 조회 `www.lotteon.com`). ②**판정** — `Disallow: /` 한 줄만 봐서 `Disallow: /` + `Allow: /plan/front/` 인 곳을 전면 차단으로 오독했다. 물어야 할 질문은 "이 몰이 전면 차단인가"가 아니라 **"우리가 두드리는 그 경로가 아직 허용되는가"** 다.
- 결정: **판정 파서를 앱에 둔다.** `RobotsRules`(UA 그룹 선택 → 최장일치 Allow/Disallow → 동률 Allow 우선)와 `ProbeEndpoint` 를 신설하고, 셀프테스트 응답에 `probeEndpoints`(조회 호스트·경로)·`robotsUserAgent`(`onnuri-guide`)·`robots[]`(`allowed`·`rule`·`group`·`error`)를 싣는다. **배치는 파서를 갖지 않고 그 결과를 옮긴다** — 조회 대상 호스트는 다시 가져오지 않고(하루 두 번 두드리지 않는다), 앱이 모르는 색인 전용 호스트만 배치가 거칠게(`coarse`) 본다. 기준선 상수 `ROBOTS_BLOCKED_AT_SURVEY`·`ROBOTS_WATCH_IDS` 는 삭제하고 **어제 리포트와 비교**한다. 못 읽은 호스트는 `allowed=false`+`error` — **모르는 것을 허용으로 적지 않는다.** 킬스위치가 꺼지면 robots 도 조회하지 않는다(항의를 받아 끈 상황에서 계속 두드리는 것은 모순이다) — 대신 리포트에 "확인하지 않았다"가 드러난다.
- 근거: 2026-08-31 에 단계 E 를 만들 때 세운 "배치에 파서를 두지 않는다"(앱과 배치가 다른 규칙으로 판정하면 누가 맞는지 사람이 매번 따진다)가 여기서도 그대로다. 더 결정적인 것은 **경로** — 판정이 경로 규칙을 읽어야 하는데 우리가 두드리는 정확한 경로를 아는 곳은 `ProbeTargets` 뿐이다. 배치로 넘기면 2026-08-31 굿데이 도메인 오기(감시가 조용히 다른 사이트를 보던 사고)가 형태만 바꿔 되살아난다. 기각한 대안: ①배치에 파서 — 위 이유 ②기준선 상수 유지 — 편입 때 넣는 걸 잊으면 조용히 거짓 통과 ③조회가 꺼져도 robots 는 본다 — 킬스위치의 대표 용도가 항의 대응이라 정확히 반대다.
- **오늘 기준선(2026-09-03, 조회 18곳)**: **차단 5곳** — 굿데이·인더마켓·현대홈쇼핑·롯데ON(`Disallow: /`), 공영쇼핑(`Disallow: /search/`). 나머지 13곳 허용. 전부 편입 당시 robots 상태를 알고 결정한 곳이라 새 사실이 아니다. **이 수가 늘거나 목록이 달라질 때만 알린다** — 매일 5건이 뜨는 것을 "늘 그런 값"으로 넘기기 시작하면 진짜 변화를 놓친다.
- 구현 중 발견: ①경로만 실었을 때 굿데이·인더마켓이 **허용**으로 나왔다 — 두 몰의 조회 주소는 경로가 `/` 뿐이고 검색 조건이 전부 쿼리에 있어 그 몰들의 `Allow: /$`(루트만 연다)에 정확히 걸렸다. robots 매칭은 경로와 쿼리를 함께 보므로 쿼리를 붙이자 `Disallow: /` 로 뒤집혔다(질의어 자리는 고정 토큰이라 이용자 검색어는 실리지 않는다) ②배치 스캐너가 **404 가 아닌 HTTP 오류도 "금지 없음"으로 적고 있었다** — 301 루프·403 이 "허용"으로 남는다. 404·410 만 "파일 없음 = 금지 없음"이고 나머지는 관측 실패다.
- 결과·롤백: 아웃바운드는 호스트 중복 제거로 **평시 하루 57건**(dev-qa 6차 실측) — 카나리아 36(18곳×2질의) + 앱 robots 18(호스트당 1회) + 배치 coarse 3(색인 호스트). **중복 0**(조회 18호스트 ∩ 색인 3호스트 = 공집합). 킬스위치 OFF 면 색인 3건만, 조회·색인 둘 다 꺼지면 0건. 자동 비활성화는 하지 않는다(ADR-17 이 기각한 조용한 축소) — 리포트와 WARN 까지다. 롤백 = 셀프테스트 3필드 제거 + 배치를 이전 상수 방식으로.

## ADR-22: 관측은 **출처**를 확인한다 — 받은 것이 그 몰에서 온 것인가 (2026-09-05)
- 맥락: 야간 배치가 `hyundai-ezwel-onnuri [present] 기대=likely 실제=none` 을 냈다 — **있는 질의를 없다고** 했고, ADR-17 이 세 갈래 중 가장 위험하다고 적은 방향이다. 원인은 판정 규칙이 아니었다. 이지웰이 서비스 점검에 들어가며 `www.onnuri-sijang.com/...` 요청을 `withus.ezwel.com/maintenance/index.html` 로 302 보냈고, 우리 수집기는 리다이렉트를 따라가므로(`Redirect.NORMAL`) 최종 응답이 **200 · 8KB 짜리 멀쩡한 HTML** 이라 상태코드 가드도 2026-08-31 의 응답 길이 가드도 통과했다. 그 안에 상품도 없음-문구도 질의어도 없어, `echoesQuery=false` 몰의 **"질의어 0회 = 없음"** 조건을 완벽히 만족했다. 같은 함정이 robots 조회에도 있었다 — `robots.txt` 요청이 같은 안내 페이지로 넘어가 **HTML 을 robots.txt 로 파싱**하고 `allowed:true` 로 보고하고 있었다(그 몰의 진짜 robots 도 제약이 없어 결과가 우연히 같았을 뿐이다).
- 결정: **판정·파싱 앞에서 출처를 본다.** 최종 응답의 호스트가 요청 호스트와 다르면 그 본문을 쓰지 않는다 — 조회는 `redirected` 사유로 '못 받았다', robots 는 관측 실패(ADR-21 이 error 를 차단 집계와 분리해 뒀으므로 '금지 없음'으로도 '전면 차단'으로도 세지 않는다). **네 층 모두**에 넣었다: 실시간 조회(`ProbeFetcher.fetch`) · robots 조회(`ProbeFetcher.robotsBodyOrThrow`) · 배치 스캐너(`_robots_scan`) · 그리고 판정 자체(없음-문구 사전을 가진 몰은 토큰 0 만으로 '없음'을 확정하지 않는다 — 출처 가드는 *다른* 호스트만 막고 **같은 호스트 안의 점검 페이지**는 그대로 들어오기 때문).
- 근거: 조회 대상 18곳의 최종 호스트를 전수로 재 **17곳이 요청 호스트에 그대로 머물고 벗어난 곳은 점검 중인 이지웰 하나**임을 확인한 뒤 정확히 같은 호스트를 요구하기로 했다. 기각한 대안 — ①**등록가능 도메인 비교**(www→m 을 허용): Java 에 PSL 이 없어 `co.kr` 을 잘못 자르고, 무엇보다 어떤 몰이 정당하게 옮겨 가면 **카나리아가 알려 주는 편이 낫다**(그때 결과는 '확인 못 함'이지 '없다'가 아니라 안전한 방향이다) ②**내용으로 판별**(점검 페이지 문구 사전): 몰마다 다르고 ADR-6 이 경계한 몰별 정규식이 판정 경로에 들어온다 ③**리다이렉트를 아예 따라가지 않는다**: 같은 호스트 안의 경로 이동은 흔해서 멀쩡한 몰이 깨진다. 판정 조임의 **대가**도 명시한다 — 없음-문구를 가진 8곳의 문구가 바뀌면 종전에는 토큰 0 이 조용히 받아 주던 것이 `unclear` 가 된다. 잘못 '없다'고 하면 이용자는 그 몰을 아예 안 보지만 '모르겠다'면 늘 함께 주는 링크를 눌러 보면 되므로 비대칭이 분명하다.
- 결과·롤백: backend `ProbeFetcher`(sameHost·robotsBodyOrThrow)·`ProbeOutcome.REDIRECTED`·`ProbeJudge`(토큰 0 조건)·`SelfTestService`(실패 사유에 메시지), `backend/tools/nightly_update.py`(_robots_scan), `online-probe.js?v=16`(사유 문구 `다른 곳으로 연결됨`). 롤백은 커밋 단위로 갈라 뒀다 — 출처 가드 `7ac10b5`(조회)·`f51bff2`(robots)·`487a83f`(배치), 판정 조임 `ea38f5b` 하나만 따로 되돌릴 수 있다. **색인 층(단계 F)은 손대지 않았다** — 점검 페이지를 받으면 sitemap 에서 `<loc>` 를 못 찾아 그 회차가 실패하고 커버리지 50% 가드가 기존 색인을 지킨다(확인함).
- 교훈: **판정 규칙을 아무리 정교하게 만들어도 엉뚱한 페이지를 판정하면 소용이 없다.** 2026-08-31 의 응답 길이 가드는 에러 페이지를 막으려는 것이었는데 "짧은 응답"만 봤고, 점검 안내 페이지는 8KB 짜리 정상 HTML 이라 그 그물을 통과했다. 이 가드는 내용이 아니라 출처를 본다. 그리고 **가드는 층마다** 넣어야 했다 — 한 층만 고치면 같은 몰을 두고 앱과 배치가 다른 말을 한다(ADR-21 이 파서를 앱에 둔 논리와 같다).
