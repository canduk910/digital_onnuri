  - 이유: "부족분만 카드 청구"는 confidence **medium**이고, 공식몰 원문("충전액보다 결제액이 크면 차감·병행 결제 없이 일반카드로 한 번에 결제")과 상충. medium은 단정 금지 — 두 동작 병기 + 확인 지시가 스킬 규칙에 맞는 어조.

### S10. 모바일(앱)형 결제 흐름 — **신규**
S9와 같은 아코디언 패턴으로 바로 옆(아래)에 배치.
- 제목: `모바일(앱)형 결제 흐름 — QR 방식`
- 부제: `실물 카드 없이 앱만으로 — QR을 찍거나 보여주고 잔액에서 바로 차감`
- 단계:
  - `1 · 앱 설치·가입 — '디지털온누리' 통합앱 설치 후 본인 명의 휴대폰으로 가입 (2025.3.1부터 카드형·모바일형이 이 앱 하나로 통합 — 한국조폐공사 운영)`
  - `2 · 충전 — 앱에서 충전하면 곧 상품권 잔액 — 할인 적용, 월 한도 내 (카드형과 동일)`
  - `3 · QR 결제 — 앱의 'QR 결제'에서 가맹점 QR을 스캔해 금액을 입력하거나, 내 QR을 만들어 점주에게 제시`
  - `4 · 인증·차감 — 간편비밀번호·지문 등으로 인증하면 충전 잔액에서 차감`

## S16. 온라인 사용처 찾기 (online.html) — 2026-08-10 신설

**목적:** 온라인 가맹 플랫폼 30곳을 (1)물품종류(대분류→소분류 계층) (2)브랜드 2축으로 조회. 데이터 수준은 **플랫폼 단위 태깅**(상품 아님) — 각 몰 실측(15_online_catalog_report.md).

**정보구조:** 구분 탭(전체/쇼핑/배달, 숫자 주인공) → **1단계 물품종류 대분류 칩(단일 선택)** → **2단계 세부 칩(다중 선택, 상위에 종속)** → 브랜드 칩(상위 10)+**브랜드 검색 팝업** → 검색·'전국 이용 가능만' 토글 → 카드 그리드(플랫폼명·구분/지역한정 배지·summary·물품태그(선택 우선 정렬·8개 초과 접기)·브랜드 태그·방문 ↗).

**물품종류 단계 필터(2026-08-27 개편):** 소분류를 35종까지 채록해 놓고 정작 고를 수 없던 것을 고쳤다 — 종전에는 대분류가 다중이라 2개 이상 고르면 소분류 행이 통째로 사라졌다. 규칙: ①1단계 대분류는 **단일 선택**(해제는 '전체'로), ②2단계는 그 대분류의 subs만 노출하고 **다중 OR**, ③상위를 바꾸면 하위는 '전체'로 리셋, ④선택 전 기본값은 각 단계 '전체'. 소분류가 없는 대분류(뷰티·출산유아 등)는 2단계를 숨기지 않고 "이 분류는 세부 항목이 없습니다 — 위 단계 결과가 곧 전체입니다"를 표시한다 — 단계가 갑자기 사라지면 이용자는 조작을 잘못한 줄 안다.

**소분류 판정 엄격화(2026-08-27):** `hasCat`이 소분류를 물을 때 **부모 id 만 가진 몰도 매칭**시키던 것을 없앴다. 소분류가 농·수·축 3개에만 있던 시절엔 합리적이었으나, 35종을 채록한 지금은 "김치를 확인하지 못한 곳"까지 김치 필터에 넣어 결과를 부풀린다(실측: 김치 10곳 → 19곳). 대신 빠지는 곳을 카운트 문구에 병기한다 — `… · 세부 미확인 N곳 제외`. 숫자를 줄이는 방향의 정정이므로 **왜 줄었는지를 화면이 말해야** 한다(부분노출 안내 원칙).

**브랜드 검색 팝업(2026-08-27, 드롭다운 대체):** 178종을 한 줄 `<select>` 로 훑게 하던 것을 merchants.html 과 같은 구조·클래스명의 모달로 바꿨다(부분검색 + 초성/알파벳 색인 + 다중 토글). 트리거는 칩 줄 맨 앞의 오렌지 아웃라인 버튼 + 숨은 종 수 배지(`브랜드 검색 +168종`). merchants 와 다른 점 두 가지 — ①데이터가 이미 메모리에 있어 비동기 로드·로딩 상태가 없다, ②**고를 때마다 닫지 않는다**(로컬 필터라 즉시 반영되고 브랜드를 겹쳐 보는 사용이 흔하다). 헤더에 'N개 선택', 하단에 '선택 해제'·'닫기'. **카드 태그 접기(2026-08-27):** 소분류 35종이 되며 한 몰에 태그가 20개를 넘어 카드 하나가 화면을 다 차지했다(실측 306px→그 이상). 브랜드 줄과 같은 방식으로 8개까지만 펴고 나머지는 `+N`. 단 **선택과 맞는 태그는 앞으로 끌어오고 잘리지 않는다** — 지금 보고 있는 조건이 카드에서 사라지면 안 된다. 강조(`hit`)는 고른 단계를 따른다: 소분류를 골랐으면 그 소분류만 칠한다(대분류 하위를 전부 칠하면 실측에서 9개가 한꺼번에 강조돼 어느 게 김치인지 안 보였다).

## S19. 온라인 실시간 조회 (online.html + online-probe.js) — 2026-08-31 신설, ADR-17 · 2026-09-02 전일 색인 층 추가, ADR-18

플랫폼 태그 검색은 "이 몰이 무엇을 파는지"까지만 답한다. 이용자가 실제로 묻는 것은 "그 상품이 있느냐"다. 검색어를 넣으면 배너가 뜨고, **Enter 또는 버튼으로** 조회 대상 몰을 동시에 조회한다.

**곳 수는 이 명세에 적지 않는다.** 조회 대상은 서버(`ProbeTargets`)가 정하고 화면은 서버가 만든 `notice` 를 그대로 출력한다. 여기에 숫자를 박으면 대상이 늘 때마다 명세가 조용히 거짓이 된다(실제로 6→7→9→10곳으로 늘었다).

### 문체 원칙

| 원칙 | 이 화면에서 |
|---|---|
| 단정 강도를 근거에 맞춘다 | 판정에 "있음"이 없다. 가장 강한 표현이 `관련 상품이 검색됨`이다. `none`만 `검색 결과가 없습니다`로 단정하고, 그것도 **확인한 몰 안에서만** 참이다 |
| 부분만 보여줄 땐 그렇다고 말한다 | 헤드라인 마지막 문장이 `나머지 N곳은 확인하지 않았습니다 — 없다는 뜻이 아닙니다`. 그 N곳은 접힌 섹션에 링크로 전부 있다 |
| 날짜를 문장에 심는다 | 각주에 `확인 시각 YYYY-MM-DD HH:mm`. "방금"·"최근"을 쓰지 않는다 |
| 규칙 하나에 장면 하나 | `likely`에는 실제 상품명 3건을 붙이고 `이름이 비슷한 다른 상품일 수 있습니다`를 병기한다. "로보락 큐레보"를 찾으면 "호환 리필 물걸레"가 걸리는 일이 실제로 있다 |
| 용어는 처음 쓸 때 푼다 | 배너에서 `몰 단위 태그`(내부 용어)를 쓰지 않고 `어느 몰이 무엇을 파는지까지만 알고 있어서`로 풀어 쓴다 |

### 문구

| 자리 | 문구 | 이유 |

| 배너 — 로컬 결과 0곳 | `지금 목록은 **어느 몰이 무엇을 파는지**까지만 알고 있어서 '{q}' 같은 상품명은 걸리지 않습니다.` | 원인을 밝히지 않고 "조건에 맞는 플랫폼이 없습니다"만 띄우면 조용한 실패다 |
| 배너 — 로컬 결과 있음 | `'{q}' 상품이 실제로 있는지 여러 몰을 동시에 조회해 확인할 수 있습니다.` | 위와 같은 이유 |
| 검색창 상시 안내 | `상품명을 넣어 보세요 — 목록에 없어도 **여러 온라인몰을 동시에 조회해** 그 상품이 있는지 확인합니다.` | 2자를 입력하기 전에는 이 기능이 있다는 사실 자체를 알 수 없었다 |

| 헤드라인 | **서버의 `notice`를 그대로 출력** | 프론트가 `items.filter()`로 재계산하면 계약 변경 시 조용히 틀린 숫자가 나온다 |
| 상태 라벨 | `관련 상품이 검색됨` / `검색 결과가 없습니다` / `판정하지 못했습니다` / `확인하지 못했습니다` / `확인하지 않았습니다` | |

### 조회하지 않는 이유 — 3종 (2026-09-02, ADR-18)

사유를 전수로 적는 이유: 예전에는 사전에 robots 몇 곳만 적고 **나머지를 기본값 `no-static-search` 로 흘렸다.** 그래서 화면이 "화면에서만 만들어져 읽을 수 없음"이라고 말했는데, 그 문구는 대상 몰 어디에도 정확히 맞지 않았다. 사유를 잘못 대는 것은 사유를 안 대는 것보다 나쁘다 — 이용자가 우리 사정으로 읽고 넘긴다.

| `reason` | 짧은 배지 | 접힌 섹션 설명 |
|---|---|---|
| `robots-blocked` | `몰이 자동 조회를 막아 둠` | `이 몰은 robots.txt로 자동 조회를 막아 뒀습니다. 링크로 들어가 직접 검색하는 것은 정상 이용입니다.` |
| `scope-first` | `시장·주소를 먼저 고르는 구조` | `시장이나 배달 주소를 먼저 골라야 상품이 나오는 몰이라 한 번에 조회할 수 없습니다.` |
| `no-static-search` | `자동 조회가 안 되는 구조` | `검색 결과가 화면에서만 만들어지고 검색 API 는 인증이 필요해 자동으로 읽을 수 없습니다.` |

`robots-blocked` 에 **"링크로 들어가 직접 검색하는 것은 정상 이용입니다"** 를 병기하는 이유는 그대로다 — 이 구분을 말하지 않으면 "쓰면 안 되는 몰"로 읽힌다.

**해당하는 몰이 없어진 사유 라벨은 지운다.** `no-search-feature`(검색 기능이 없는 몰)는 그 몰이 실시간 조회 대상으로 승격되면서 붙는 곳이 0이 되어 제거했다 — 2026-09-01 `rules-unverified` 를 지운 것과 같은 원칙이다. 아무에게도 해당하지 않는 사유가 목록에 남아 있으면 이용자는 그 사유의 몰이 어딘가 있다고 읽는다.

**묶음 순서는 성격순**: 허락(robots) → 범위 선행 → 기술적 불가. 곳 수순이 아니다 — 곳 수는 데이터가 바뀌면 순서를 뒤집는데, 이용자가 읽는 흐름("우리가 못 하는 이유가 서로 다르다")은 바뀌지 않는다. **곳 수는 이 명세에 적지 않는다** — 서버 데이터에서 센다.

**모르는 사유가 오면 영문 키를 화면에 찍지 않는다.** 서버가 사유를 더하거나 빼는 배포 시차에 `no-search-feature` 같은 키가 이용자에게 그대로 보이면 안 된다. 행 배지는 생략하고(상태 라벨이 이미 뜻을 담는다), 접힌 섹션은 어느 비대상 몰에도 참인 `자동 확인 대상 아님` 으로 물러선다 — 없는 사유를 지어내지 않는다.

### 전일 색인 층 (2026-09-02, ADR-18)

실시간 조회 대상이 아닌 몰 일부는 야간 배치가 **상품명만 미리 모아 둔다.** 그 색인에서 찾은 결과를 실시간 결과 아래에 **별도 층**으로 붙인다. 어느 몰이 어느 층에 속하는지는 서버(`ProbeTargets` · 색인 적재 대상)가 정하므로 **여기에 몰 이름도 곳 수도 적지 않는다** — 조회 대상은 실제로 6→7→9→10→11곳으로 늘어 왔고, 적는 순간 명세가 조용히 거짓이 된다.

**두 층을 한 목록에 섞지 않는다.** "어제 이 이름의 상품이 올라와 있었다"와 "지금 검색된다"는 다른 주장이다. 섞는 순간 헤드라인의 곳 수가 거짓이 되고, 이용자는 색인 결과를 지금 살 수 있는 것으로 읽는다. 그래서 별도 블록·별도 헤드라인·한 단계 약한 시각 위계(회색 톤, 오렌지는 링크에만)로 두고, 블록 맨 위에 `전일 색인` eyebrow 를 박는다.

| 자리 | 문구 | 이유 |
|---|---|---|
| 블록 eyebrow | `전일 색인` | 층 이름을 먼저 말하지 않으면 아래 항목이 실시간 결과의 연장으로 읽힌다 |
| 헤드라인 | **서버 `index.notice` 를 그대로 출력** — 4분기: 색인 몰 없음 → `null`(블록 없음) / 전체 일치 N≥1 → `전일 색인: N곳에서 검색어 전체를 담은 상품명을 찾았습니다(YYYY-MM-DD 수집 기준). 어제 올라와 있던 이름이라, 지금 재고와 온누리 결제 가능 여부는 몰에서 확인하세요.` / 전체 일치 0·부분 M≥1 → `전일 색인: 검색어 전체를 담은 상품명은 없고, 일부 낱말만 맞는 상품명이 M곳에 있습니다(YYYY-MM-DD 수집 기준). 찾는 상품이 아닐 수 있습니다.` / 둘 다 0 → 아래 '항목이 하나도 없을 때' 행 | 실시간 헤드라인과 같은 원칙. 프론트가 `items` 로 곳 수를 재계산하면 계약 변경 시 조용히 틀린다(2026-08-27 `normKind` 유형). 원천은 `OnlineSearchService`/`IndexJudge` — 문구를 바꾸면 여기와 서버를 함께 고친다 |
| 항목 — 전체 낱말 일치 있음 | `상품명 {matchCount}건 발견` | 건수는 서버 `matchCount`. "있습니다"가 아니라 "발견"인 이유는 그것이 **어제 색인에서 찾은 이름**이지 지금의 재고가 아니기 때문 |
| 항목 — 전체 낱말 일치 없음 | `검색어 전체와 맞는 이름은 없었습니다` | 샘플이 부분 일치뿐일 때 이 말을 먼저 하지 않으면 샘플이 "찾았다"로 읽힌다 |
| 샘플 아래 한 줄 | 실시간 층과 **같은 문구** — `samplePartial` true면 `검색어의 일부 낱말만 맞는 결과입니다 — 찾는 상품이 아닐 수 있습니다.`, false면 `이름이 비슷한 다른 상품일 수 있습니다 — 몰에서 확인하세요.` | 낱말 분리는 서버 규칙(`ProbeQuery`) 하나다. 두 층이 다른 말을 하면 같은 사실이 층마다 달라 보인다 |
| 항목 스탬프 | 항목 `collectedOn` 이 `index.asOf` 와 다를 때만 `YYYY-MM-DD 수집분` 병기 | **확인하지 않은 날짜를 올리지 않는다**(온라인 스탬프 규칙과 같음). 한 몰만 뒤처졌으면 그 몰에만 적는다. **날짜가 갈리는 것 자체가 신호다** — 아래 참조 |
| 링크 | `몰에서 보기 ↗` (새 탭) | 실시간 층과 같다. 색인은 어제 것이므로 지금 확인할 곳을 반드시 준다 |
| 항목이 하나도 없을 때 | 서버 `index.notice` 를 그대로 — `전일 색인 N곳(YYYY-MM-DD 수집 기준)에는 이 검색어를 담은 상품명이 없습니다 — 색인에 없다는 뜻이지, 그 몰에 없다는 확정은 아닙니다.` | **이 층에서 가장 중요한 문장이다.** 색인은 몰이 파는 것의 전부가 아니라 배치가 걷어 온 만큼이다. 이 단서가 없으면 이용자가 "그 몰엔 없다"로 확정해 버린다 |
| 각주(색인 있을 때) | `확인 시각 … · 위 목록은 각 몰의 검색 결과를 그 자리에서 읽은 것이고, 전일 색인은 미리 모아 둔 상품명에서 찾아본 결과입니다. **검색된다고 해서 온누리상품권으로 결제된다는 뜻은 아닙니다** — 상품 상세와 결제 수단은 몰에서 확인하세요.` | 각주는 맨 아래 한 번뿐이라 **두 층을 다 덮어야 한다.** "찾은 것입니다"로 쓰면 아무것도 못 찾은 회차에서 각주가 거짓이 된다 |

**`수집분` 병기는 장식이 아니라 부분 실패 경보다** (2026-09-02 backend 확인). 색인 몰이 같은 날 밤에 함께 걷히면 `asOf` 와 모든 항목의 `collectedOn` 이 같은 날짜가 된다. 날짜가 갈리는 경우는 **한 몰의 수집이 실패해 이전 회차 색인이 그대로 유지될 때**뿐이다(배치 가드가 그렇게 설계돼 있다). 즉 이 병기는 "이 몰만 어제 것이 아니라 그 이전 것"이라는 뜻이고, **이용자가 그 사실을 알 수 있는 유일한 통로다.** 화면이 조용해지는 쪽으로 이 표시를 지우면 안 된다 — 2026-09-01 가맹점 수집 중단이 나흘간 아무에게도 안 알려졌던 것과 같은 유형의 침묵이 된다.

**배치**: 실시간 결과 목록 **아래**, `확인하지 않은 나머지 N곳` 접힌 섹션 **위**. 실시간이 먼저이고 색인은 그 보완이라는 순서를 배치가 말한다.

**블록을 그릴지는 `platformCount`·`notice` 로만 판단한다 — `items` 로 판단하지 않는다.** 색인해 둔 몰은 있는데 그 검색어를 담은 이름이 하나도 없는 경우가 **정상**이고, 그때가 바로 위 "색인에 없다는 뜻이지, 그 몰에 없다는 확정은 아닙니다" 문장이 나가야 할 자리다. `items` 로 접으면 이용자는 색인이 답했다는 사실조차 모른 채 실시간 결과만 보고 "없다"로 접는다. 다만 항목 목록(`<ul>`)은 행이 있을 때만 만든다 — 빈 목록은 경계선만 남긴다.

`platformCount == 0` 이거나 `notice` 가 없으면 블록 자체가 없다. 기능이 조용히 사라지는 것이 아니라 이 검색어에 색인이 답할 것이 없는 것이고, 실시간 층은 그대로 나온다. 실시간이 실패(오류·지연)해도, 킬스위치가 꺼져 있어도, 캐시가 적중해도 색인은 매번 새로 계산돼 오므로 블록은 그린다.

### 배치와 강조

검색창을 **필터보다 위**에 둔다. 실시간 조회가 붙으면서 검색이 이 페이지에서 가장 강한 도구가 됐는데 칩 4줄 아래에 있어 위계가 가장 낮았다(2026-09-01 실측 y=542 → 275). 조회 배너·결과도 검색창 바로 아래에서 열린다 — 상품명으로 찾으면 로컬 결과는 대개 0곳이라 실시간 결과가 그 화면의 주인공이다.

위치를 옮긴 것만으로는 눈에 띄지 않아(2026-09-01 사용자 지적) **오렌지로 감쌌다** — 연오렌지 바탕(`--accent-soft`) + 왼쪽 4px 오렌지 바 + 오렌지 테두리의 흰 입력창 + 오렌지 아이콘 + `상품 실시간 검색` eyebrow. 이 페이지의 칩·탭은 전부 모노톤이라 오렌지 블록이 여기 하나뿐이고, 그래서 "오렌지는 포인트만"이라는 디자인 원칙과 충돌하지 않는다. 대비 실측 — eyebrow·강조어 4.25:1(굵은 소자 AA 3.0 통과), 안내 본문 6.08:1, 입력 19.57:1.

조회 배너·결과 상자는 히어로 안으로 들어가므로 **흰 배경**으로 되돌렸다. 오렌지 위에 오렌지를 겹치면 둘 다 죽는다.

### 챗봇이 보내는 카테고리 형식 (2026-09-02)

챗 이동 액션의 `cat` 은 **`대분류/소분류`** 로 온다 — RAG 코퍼스가 카테고리를 그 형식으로 적기 때문이다(`가전·디지털/생활·주방가전`). 화면은 `applyCat()` 창구 하나에서 소분류 id·라벨, 대분류 id·라벨, 슬래시 형식을 모두 받는다. 챗 훅과 URL 파라미터가 같은 창구를 지난다 — 입력 지점이 늘어도 한 곳만 고친다(2026-08-27 `normKind` 와 같은 방식).

이 창구가 없을 때는 어느 것과도 맞지 않아 **필터가 통째로 무시됐다**(실측 22곳 = 쇼핑 전체, 정상이면 10곳).

### 품목으로 찾기 (2026-09-02)

이름·태그 라벨에 그대로 없는 말도 **품목으로 한 번 더** 찾는다. `"로봇청소기"` 는 0곳이었다 — taxonomy 라벨이 `생활·주방가전` 까지만 내려가고, **몰 메뉴 원문에도 그 문구가 없다**(6곳 재채록으로 확인). 그래서 소분류를 더 쪼개는 것으로는 풀리지 않는다.

대신 채록에 쓰는 판정 규칙(`CAT_RULES`)이 이미 `청소기` 를 `생활·주방가전` 으로 옮길 줄 안다. **같은 규칙을 화면 검색에도 쓴다** — 새 동의어 사전을 만들지 않는다. 규칙의 출처는 코드 한 곳이고 `data/cat_rules.json` 은 그 사본이며, 어긋나면 테스트가 실패한다.

| 자리 | 문구 | 이유 |
|---|---|---|
| 카운트 | `30곳 중 13곳 표시 · **품목으로 찾은 13곳 포함**` | 직접 일치가 아니라는 사실을 밝힌다. 곳 수는 계산값이다 |
| 카드 태그 | 검색어가 가리킨 태그를 **앞으로 끌어와 강조** | 없으면 "로봇청소기로 찾았는데 농산물 태그가 보이는" 상태가 된다 — 왜 걸렸는지 알 수 없다 |

실측: 로봇청소기 0→13곳 · 노트북 6 · 선풍기 9 · 기저귀 11. 김치·다이슨은 라벨·브랜드에 직접 있어 품목 표기가 붙지 않는다. 없는 말은 0곳 그대로.

### 하지 않은 것

- **타이핑 자동 조회.** 글자마다 여러 곳을 두드리면 상대 사이트 부담이 통제 불능이 된다(ADR-16과 같은 근거). 사람이 실행을 지시한 뒤에만 나간다 — 버튼 클릭 **또는 Enter**. Enter 를 받아들이는 것은 이 원칙과 충돌하지 않는다. 막으려던 것은 "한 글자마다 나가는 것"이지 사람의 실행 의사표시가 아니다. 단 **한글 조합 중의 Enter 는 조합 확정이지 실행이 아니므로** 걸러낸다(2026-08-12 챗 입력창과 같은 함정).
- **배달 8곳 조회·링크.** 음식 주문이라 상품명 검색 축이 성립하지 않는다.
