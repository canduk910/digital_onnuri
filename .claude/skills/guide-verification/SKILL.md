# 가이드 교차 검증

각 단계가 개별적으로 옳아도 **연결 지점에서 어긋나는 것**이 이 프로젝트의 실제 결함이다. 상세 체크리스트는 `references/crosscheck-checklist.md` 참조.

## 검증의 기본 동작: 양쪽을 동시에 읽는다

한쪽만 보면 모든 것이 정상으로 보인다. 데이터 파일만 읽으면 완벽하고, 페이지만 읽어도 완벽하다. 결함은 둘 사이에만 존재한다.

| 경계면 | 왼쪽 (생산자) | 오른쪽 (소비자) | 잡는 결함 |
|--------|-------------|---------------|----------|
| B1 출처 → 데이터 | 온누리 공식 홈페이지 | `data/*.json` | 누락, 폐점 미반영 |
| B2 데이터 → 렌더 | `data/*.json` 항목 수 | 페이지 행 수·요약 숫자 | "30곳"인데 28행 |
| B3 정책 → 문구 | `01_policy_analysis.md` | 페이지 본문 문장 | 시행일 오기, 근거 없는 단정 |
| B4 수집일 → 스탬프 | 각 항목 `collected_on` | 페이지 "○○ 기준" | stale stamp |

## B4가 가장 위험하다

날짜 스탬프는 **양방향으로** 결함이 된다:

- 데이터를 갱신했는데 스탬프가 그대로 → 이용자가 최신 정보를 낡은 것으로 오해하거나, 낡은 정보를 최신으로 믿는다
- 데이터는 그대로인데 스탬프만 올림 → **검증되지 않은 정보에 신뢰를 부여한 것.** 이것이 더 나쁘다

검사식: 페이지 스탬프 ≤ `min(items[].collected_on)`.

부분 수집이 있었다면 미확인 항목의 `collected_on`은 올라가지 않았어야 한다. 전체 항목의 `collected_on`이 일제히 같은 날짜로 되어 있는데 수집 리포트에 접근 실패 기록이 있다면, 그것은 확인하지 않은 항목까지 날짜를 올린 것이다.

## 존재 확인이 아니라 교차 비교

| 약한 검증 | 강한 검증 |
|----------|----------|
| 표가 있는가 | 표의 행 수가 데이터 항목 수와 같은가 |
| 기준일이 표기되어 있는가 | 기준일이 실제 수집일과 일치하는가 |
| 요건이 설명되어 있는가 | 문장의 단정 강도가 confidence를 넘지 않는가 |
| 조건부 항목이 있는가 | 조건부 항목마다 확인 방법이 제시되는가 |

## 렌더 검증은 실제로 열어서 한다

코드를 읽는 것만으로는 렌더 결함을 못 잡는다. `index.html`을 브라우저로 열어 확인한다.

브라우저 도구는 deferred다. 한 번의 `ToolSearch` 호출로 필요한 것을 함께 로드한 뒤 `file://` 절대 경로로 연다 — 개별 로드는 매번 왕복 비용을 낭비한다:

```
ToolSearch("select:mcp__claude-in-chrome__tabs_context_mcp,mcp__claude-in-chrome__tabs_create_mcp,mcp__claude-in-chrome__navigate,mcp__claude-in-chrome__read_page,mcp__claude-in-chrome__read_console_messages,mcp__claude-in-chrome__resize_window")
```

1. **콘솔 에러 확인** — 조용한 JS 에러 하나가 표를 통째로 비운다. 코드 리뷰로는 절대 안 잡힌다
2. **화면에서 숫자를 센다** — 헤더의 요약 숫자와 실제 행 수를 눈으로 대조
3. **검색을 해본다** — 필터가 동작하는지, 결과 없음 상태가 다음 행동을 안내하는지
4. **좁은 폭으로 리사이즈** — 표가 깨지지 않는지, 페이지가 가로로 밀리지 않는지

## 점진적으로 검증한다

전체 완성 후 한 번에 검증하지 않는다. 산출물이 나오는 즉시 해당 경계면을 검증한다:

- 데이터가 나오면 → B1 (출처 ↔ 데이터)
- 문구가 나오면 → B3 (정책 ↔ 문구)
- 페이지가 나오면 → B2, B4 (데이터 ↔ 렌더, 스탬프)

초기 불일치가 뒤 단계로 전파되면 수정 비용이 몇 배가 된다. 잘못된 데이터 위에 쓴 문구는 문구도 다시 써야 한다.

## 미검증과 통과를 구분한다

공식 출처에 접근하지 못해 B1을 확인하지 못했다면, 그것은 **미검증**이지 통과가 아니다. 리포트에서 두 상태를 절대 섞지 않는다. 섞이는 순간 리포트는 "확인했다"는 거짓 신호를 준다.

## 결함 보고 형식

"이상하다"가 아니라 **양쪽에서 관측한 값**으로 말한다. 담당 에이전트가 재현할 수 있어야 한다.

```markdown
### D1. 온라인 플랫폼 요약 숫자와 표 행 수 불일치
- 심각도: 높음
- 경계면: B2
- 왼쪽(관측): data/online_platforms.json — active 항목 32개
- 오른쪽(관측): index.html 온라인 섹션 부제 — "공식 안내 30곳"
- 이용자 영향: 목록이 불완전하다고 오해하거나, 신규 플랫폼을 못 찾는다
- 담당: guide-frontend-dev (부제가 하드코딩됨), guide-content-writer (동적 문구 명세 누락)
- 수정 제안: 부제를 activeCount 계산식으로 교체
```

**경계면 결함은 양쪽 담당자 모두에게 알린다.** 한쪽만 고치면 반대 방향으로 다시 어긋난다.

## 심각도 기준

| 등급 | 기준 |
|------|------|
| 치명 | 이용자가 결제 실패·헛걸음을 한다 (불가한 곳을 가능으로 안내, 시행일 오기) |
| 높음 | 정보가 불완전하거나 낡았다 (카운트 불일치, stale stamp) |
| 보통 | 정보는 맞지만 찾기 어렵다 (구조·문구 문제) |
| 낮음 | 표현·일관성 |
