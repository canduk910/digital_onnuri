# 온누리 가이드 오케스트레이터 — 2팀 체제

디지털온누리 가이드를 만드는 두 팀을 조율한다. **업무팀**은 "무엇을 말할 것인가"(콘텐츠·데이터의 정확성), **개발팀**은 "어떻게 동작할 것인가"(기능·API·구조)를 소유한다.

## 실행 모드: 에이전트 팀

이 세션에는 `TeamCreate`가 없다. 팀은 다음 조합으로 구성한다:

- `Agent(name: "...", subagent_type: "...", model: "opus")` — 팀원 스폰. `name`으로 `SendMessage` 주소 지정
- `SendMessage({to: name})` — 팀원 간·리더와의 직접 통신
- `TaskCreate` / `TaskUpdate` / `TaskGet` — 공유 작업 목록

**시작 전에 도구를 먼저 로드한다** (미로드 호출은 InputValidationError — 첫 번째 실패 지점):

```
ToolSearch("select:SendMessage,TaskCreate,TaskUpdate,TaskGet,TaskList")
```

## Phase 0-A: 라우팅 — 어느 팀을, 몇 명이나 기동할지

**팀 기동은 비싸다.** 요청을 먼저 분류한다:

| 요청 유형 | 라우팅 |
|---|---|
| 콘텐츠·데이터·문구·정책 (가이드 갱신, 목록 변경, 문구 개편) | **업무팀** — 워크플로 A |
| 기능 개발·API·버그·리팩토링 (필터 추가, API 확장, 구조 변경) | **개발팀** — 워크플로 B |
| 두 팀에 걸침 (데이터 스키마 변경→적재→렌더, 정책 변경이 기능을 요구) | **혼성** — 워크플로 C |
| 단일 단계로 끝남 | **팀을 띄우지 않는다** — description의 개별 스킬 직행 표 |
| 판단이 애매함 | 손대야 하는 산출물 수를 센다. 2개 이상이면 팀 |

**개발팀도 전원 기동이 기본이 아니다.** 프론트만 걸치면 frontend+dev-qa 2인, 계약 변경이면 backend+frontend+dev-qa 3인, 구조 쟁점이 있을 때만 architect를 추가한다.

## Phase 0-B: 컨텍스트 확인

`_workspace/`·`data/`·산출물 존재로 실행 모드를 정한다:

| 상태 | 모드 | 행동 |
|---|---|---|
| `_workspace/` 없음 | 초기 실행 | 해당 워크플로 처음부터 |
| 있음 + 부분 수정 요청 | 부분 재실행 | 해당 팀원만 스폰, 이전 산출물 경로를 프롬프트에 주입 |
| 있음 + 정기 갱신 | 갱신 실행 | 상류(policy·data)부터, 델타 없으면 하류 생략 |
| 있음 + 완전히 새 입력 | 새 실행 | 기존 `_workspace/`를 `_workspace_{YYYYMMDD}/`로 이동 |

**갱신 실행에서 델타가 없으면 멈춘다.** 변경 없는데 재생성하면 스탬프만 올라가 검증되지 않은 정보에 신뢰를 부여한다.

리더는 오늘 날짜를 확정해 모든 팀원 프롬프트에 명시한다(에이전트는 날짜를 스스로 모른다).

## Phase 0-C: 호흡 — 단발인가 긴 호흡인가

**기본은 단발이다.** 요청 하나를 처리하고 사용자에게 돌아온다. 아래 셋을 **모두** 갖췄을 때만 긴 호흡으로 들어간다.

1. 사용자가 **끝나는 시점이나 조건**을 정해 줬다("아침까지", "목록 다 할 때까지", "3시간").
2. 사용자가 **건건이 승인하지 않겠다**고 밝혔다.
3. **착수 목록이 있다.** 기본값은 `_workspace/23_backlog.md` 에 **열려 있는 항목 전체**다 — 대화에서 식별됐지만 아직 남아 있는 잔여 작업이 곧 그 목록이다. 사용자가 범위를 따로 좁혀 주면 그것을 쓴다. 사용자에게 목록을 매번 받아 오라는 뜻이 아니다.
   **목록에 없는 것은 하지 않는다.** 작업 중 새로 발견한 것은 백로그에 적고 다음 회차로 넘긴다. 여기서 범위가 새면 사용자는 자기가 승인한 적 없는 작업 결과를 아침에 받는다.

셋 중 하나라도 없으면 단발로 처리한다. 애매하면 착수 목록과 종료 조건을 한 번 확인하고 시작한다 — 이 한 번의 확인이 긴 호흡 전체의 승인을 대신한다.

### 착수 (첫 푸시가 나가기 전에 끝낸다)

- 착수 목록과 **순서**를 사용자에게 보여 준다. 목록이 백로그 전체이면 무엇을 먼저 할지만 확인받으면 된다 — 목록 자체를 다시 승인받지 않는다.
- **지금이 초록인지 확인한다.** 전 스위트를 돌려 `EXIT=0` 을 본다. 빨간 채로 시작하면 내가 낸 실패와 원래 있던 실패를 구분할 수 없다.
- 시작 커밋 해시를 기록한다. 리포트의 회차 시작점이다.

### 반복 단위 — 한 과제

작업 단위의 경계와 커밋 규칙은 **doc-commit 스킬이 정본**이다. 여기서는 긴 호흡 고유의 것만 적는다.

1. 손대기 전에 관련 전수 테스트를 돌려 현재 상태를 잡는다.
2. Red → Green → Refactor (워크플로 B).
3. **푸시 게이트**(아래)를 통과시킨다. 커밋 **전에** 돌려야 하는 것과 **뒤에** 확인할 것을 섞지 않는다.
4. 문서 갱신 → 비밀값 스캔 → 커밋 → 푸시 → 배포 결과 확인.
5. **작업 중 발견한 새 문제는 그 자리에서 고치지 않는다.** 목록에 적고 다음으로 간다. 고치기 시작하면 범위가 새고, 아침에 사용자가 받는 것은 자기가 시킨 일이 아니게 된다. 예외는 방금 내가 낸 회귀뿐이다 — 그것은 즉시 되돌린다.

### 끝나는 조건 (하나라도 걸리면 종료 절차로)

| 조건 | 행동 |
|---|---|
| 착수 목록 소진 | 정상 종료 |
| 사용자가 정한 시각 도달 | 진행 중이던 과제를 커밋 가능한 상태로 마무리하고 종료 |
| 승인이 필요한 것에 도달 | 그 항목만 남기고 다음으로. 남은 항목이 전부 그런 것이면 종료 |
| 같은 항목의 **구현 시도**가 2회 실패 | 그 항목만 보류하고 계속. 원복하고 목록에 사유를 적는다 |
| **검증 게이트 불합격** 2회 | 커밋하지 않고 원복한 뒤 그 항목을 「결정 필요」로 올린다(에러 핸들링 표의 기존 행과 같다. 긴 호흡에서도 임의 통과 금지) |
| 게이트가 두 번 연속 빨강 | 즉시 종료. 원인을 모른 채 계속하면 빨간 상태가 쌓인다 |
| 세션 한도가 가까움 | 재개 지점을 남기고 종료한다. 기다렸다 이어가는 경로는 없다 |

**어느 경우든 리포트로 마감한다.** 리포트 없이 끝난 회차는 사용자에게 전달되지 않은 회차다.

### 푸시 게이트 — "테스트가 끝났다"의 정의

푸시는 곧 배포다. 무엇이 나가는지 먼저 안다.

| 만진 것 | 자동으로 일어나는 일 | 막아 주는 것 |
|---|---|---|
| 루트 `*.html`·`config.js`·`data/**`·`assets/**` | GitHub Pages 라이브 반영 | `pages.yml` 의 checks·browser 잡이 통과해야 배포된다 |
| `backend/**` | NCP 서버에 실제 배포 | `backend-ci` 의 test·contracts 잡 |
| 무엇이든 | 다음 00:30 야간 배치가 그 커밋을 당겨 간다 | `ci_blocks_pull` 은 **확정 실패만** 막는다. 진행 중이면 그냥 당겨 간다 |

푸시 전에 **종료 코드로** 확인한다. 출력에 `FAIL` 이 없다고 통과가 아니다 — 브라우저 스위트는 실패가 아니라 종료 코드 2로 건너뛴다(dev-testing 스킬).

- 무엇을 고쳤든: 관련 전수 테스트 `EXIT=0` + 비밀값 스캔
- 루트 `*.html`·`config.js`·`data/**`: 정적 계약 + 렌더 + merchants 스모크, 셋 다 `EXIT=0`
- CSS·레이아웃: `verify_styles.js guard HEAD` — **커밋 전에** 돌린다. 커밋 뒤에 부르면 HEAD 가 이미 그 변경을 담고 있어 차이가 항상 0이고, 통과하지만 아무것도 보지 않는다
- `index.html` 재생성: D-F1
- `backend/**`: `./gradlew test`
- `_workspace/**`·`.claude/**` 문서만 고쳤다: 비밀값 스캔만. **건너뛴 사실과 변경 파일 목록을 런 기록에 남긴다** — 판단이 기록에 남지 않으면 다음번엔 페이지를 고친 커밋에서도 건너뛴다

### 푸시하지 않고 승인을 받는 것

커밋까지만 하고 푸시는 보류한다. 리포트의 결정 요청으로 올린다.

- **비밀값이 스테이징에 걸렸다** — 커밋도 중단하고 즉시 보고한다. 자율 모드에서도 예외가 없다.
- **되돌리기 어려운 것** — DB 마이그레이션(`V*.sql`), 데이터 삭제, 서버 상태 변경.
- **게이트 자체를 무르는 것** — `.github/workflows/**` 의 검사 완화, 테스트 삭제·비활성화, `skip_checks`.
- **바깥으로 나가는 것** — 새로운 외부 요청, robots 관련 정책 변경, 상대 몰에 나가는 조회 횟수를 늘리는 변경.
- **이미 "영구 종료"로 못 박은 결정**을 되돌리는 변경.

### 푸시를 미루는 것 — 승인은 필요 없다

**야간 배치 창(23:30~01:30)에는 커밋만 하고 푸시하지 않는다.** 경로를 가리지 않는다.

배치는 00:30에 시작해 맨 앞에서 `git pull` 을 한다. 그 직전에 푸시하면 게이트가 아직 돌고 있어도 배치가 그 커밋을 당겨 간다 — `ci_blocks_pull` 은 **확정된 실패만** 막고 진행 중인 검사는 그냥 통과시키기 때문이다. 시각 오차와 게이트 소요(2분 안팎)를 감안해 앞뒤로 넉넉히 잡은 창이다.

- 창 안에서는 평소대로 작업하고 커밋한다. 게이트도 평소대로 돌린다 — 미루는 것은 **푸시뿐**이다.
- **01:30이 지나면 쌓인 커밋을 한 번에 푸시하고** `gh run list` 로 게이트를 확인한다. 이것이 창이 끝난 뒤의 첫 할 일이다.
- **회차가 창 안에서 끝나면** 리포트에 `푸시 대기 N건` 을 명시하고, 그 푸시가 다음 회차의 첫 할 일임을 재개 지점에 적는다. 적어 두지 않으면 로컬에만 있는 커밋을 아무도 모른 채 며칠이 지난다.

푸시한 뒤에는 `gh run list -L 3` 으로 게이트 결과를 본다. 빨강이면 되돌리는 커밋을 즉시 푸시한다 — 그대로 자정을 넘기면 그 회차 배치가 어제 코드로 돈다.

### 마감 — 리포트

`reporter`(`subagent_type: "guide-reporter"`)를 스폰하고 이것들을 넘긴다.

1. 회차의 시작·끝 커밋 해시
2. 착수 목록과 항목별 결말(완료·보류·미착수)
3. 보류한 것과 사유
4. 커밋했지만 **푸시하지 않은 것**과 그 이유
5. 건너뛴 검사와 사유(`EXIT=2` 로 끝난 것)
6. 사용자에게 물어야 한다고 판단한 것

리포트의 절 순서·결정 요청 표·문체는 `guide-report` 스킬이 정본이다. 리더가 그것을 다시 정의하지 않는다. 리포터가 아티팩트 주소를 돌려주면 사용자에게 한 줄로 전한다. 발간에 실패했으면 HTML 경로를 받아 리더가 발간한다.

## 워크플로 A: 업무팀 (콘텐츠 파이프라인)

1. **조사 팬아웃** — `policy` ∥ `data` 동시 스폰(한 메시지, 두 Agent 호출). policy의 요건 변경은 즉시 data에 통지(판정 재계산), data의 설명 안 되는 항목은 policy에 역질의 — 이 왕복이 두 산출물을 상호 검증하게 만든다.
2. **점진 검증** — data 산출 즉시 `verifier`가 B1(출처↔데이터)만 먼저 검증. 전체 완성을 기다리지 않는다 — 잘못된 데이터 위에 쓴 문구는 문구까지 다시 써야 한다.
3. **문구** — `writer` 스폰(입력: 01·02·data/*.json) → verifier B3(정책↔문구). confidence:low 항목의 단정형 서술이 치명 등급.
4. **구현** — 페이지 반영이 필요하면 **개발팀 `frontend`를 차출**한다. 리더는 `04_build_notes.md`의 동적 문구 매핑이 콘텐츠 명세의 동적 문구 표를 빠짐없이 덮는지 확인 — 덮이지 않은 자리가 곧 하드코딩 숫자다.
5. **최종 검증** — verifier가 B2·B4와 렌더 동작(브라우저 실측). 판정: 통과 / 조건부(담당 배정 수정→재검증 최대 2회) / 불합격(2회 후 사용자 판단). 경계면 결함은 **양쪽 담당자 모두**에게 — 한쪽만 고치면 반대로 다시 어긋난다.
6. **마감(긴 호흡에서만)** — Phase 0-C 마감 절을 따른다.

## 워크플로 B: 개발팀 (TDD 사이클)

1. **설계 게이트(조건부)** — 구현 위치·구조 쟁점이 있으면 `architect` 먼저. ADR과 위임 결정문(계약·테스트 요구·롤백 포함)을 받는다. 쟁점 없으면 생략.
2. **Red** — 담당(backend/frontend)이 실패하는 테스트·검증 시나리오를 먼저 작성. dev-qa가 "테스트가 기대 동작을 표현하는가" 확인 — TDD 게이트 1.
3. **Green** — 최소 구현. 계약 변경(필드·센티넬·필터 규칙)은 서버와 프론트 JSON 폴백을 **하나의 변경 단위**로 묶는다 — 한쪽만 바꾸면 에러 없이 다른 숫자가 나온다(이 시스템 최악의 결함 유형).
4. **Refactor** — 테스트 녹색을 유지하며 정리. 구조 정리는 architect 주도 + dev-qa 사전/사후 스냅샷.
5. **검증 게이트** — dev-qa가 `./gradlew test`·Playwright·경계면 교차 비교·회귀 기준값 대조(dev-testing 스킬) — TDD 게이트 2. "미검증"을 "통과"로 쓰지 않는다.
6. **반영** — doc-commit 절차(문서→비밀 스캔→커밋·푸시. 프론트 계약+백엔드는 한 커밋). 프로덕션 반영 시 backend가 DEPLOY.md 절차 수행 + dev-qa가 프로덕션 기준값 대조.
7. **마감(긴 호흡에서만)** — 목록을 다 돌았으면 `reporter` 로 회차 리포트를 발간한다(Phase 0-C 마감 절). 단발 실행에서는 이 단계가 없다 — 리포트는 회차를 닫는 절차이지 커밋마다 하는 일이 아니다.

## 워크플로 C: 혼성 (두 팀에 걸친 변경)

데이터 스키마 변경처럼 SSOT→적재→API→렌더가 연쇄되는 요청:

1. `architect`가 변경 경로 설계(어느 층이 먼저, 계약 영향) → 결정문
2. 업무팀 `data`가 SSOT 변경 → 개발팀 `backend`가 엔티티·마이그레이션·적재기 추종 → `frontend`가 소비 갱신. 각 단계 사이 dev-qa 점진 검증.
3. 최종: **dev-qa(코드·경계면) ∥ verifier(콘텐츠·스탬프) 병렬** — 관할 상호 불가침(코드=dev-qa, 콘텐츠=verifier). 발견이 상대 관할이면 넘긴다.
4. 마감(긴 호흡에서만): Phase 0-C 마감 절을 따른다.

## 에러 핸들링

| 상황 | 전략 |
|---|---|
| 공식 사이트 접근 실패 | 미검증 기록 후 진행. 이전 값 유지, **날짜는 올리지 않는다** |
| data 항목 수 20% 이상 급감 | 수집 실패 의심 — 자동 반영 금지, 사용자 보고 |
| 테스트 인프라 다운(gradlew·서버·DB) | dev-qa가 "검증 불가" 명시, 인프라 복구를 선행 작업으로 등록 — 통과로 눙치지 않는다 |
| 회귀 기준값 불일치 | 즉시 버그 판정 금지 — 로컬 JSON 대조로 데이터 변동/버그를 분리한 뒤 처리 |
| 계약 분쟁(서버·프론트가 서로 자기 규칙 주장) | architect가 결정하고 ADR로 기록 |
| 팀원 무응답 | SendMessage 상태 확인 → 1회 재스폰 → 재실패 시 해당 산출물 없이 진행, 누락 명시 |
| 정책↔데이터 상충 | 삭제하지 않고 출처 병기, 상위 출처 채택·이유 기록 |
| 검증 2회 재시도 후 불합격 | 사용자 판단 요청. 임의 통과 처리 금지 (긴 호흡에서도 같다 — 커밋하지 않고 원복한 뒤 「결정 필요」로 올린다) |
| 긴 호흡 중 같은 항목의 **구현 시도**가 2회 실패 | 그 항목만 원복·보류하고 다음으로. 사유를 목록에 적는다. 위 행(검증 게이트 불합격)과 다른 상황이다 |
| 브라우저 스위트가 `EXIT=2` 로 끝남 | 통과로 세지 않는다. 그 층은 "확인되지 않았다"로 적고, 지도·렌더를 만진 커밋이면 푸시를 보류한다 |
| 푸시 뒤 게이트 실패 | 되돌리는 커밋을 즉시 푸시한다. 라이브는 옛 버전에 머물지만, **빨간 채로 자정을 넘기면 그 회차 야간 배치가 어제 코드로 돈다** |
| 긴 호흡 중 세션 한도 임박 | 재개 지점을 남기고 리포트로 마감한다. 기다렸다 이어가는 경로는 없다 |

## 테스트 시나리오

### 정상 — 개발팀 TDD (워크플로 B)
1. "가맹점 검색에 영업시간 필터 추가해줘"
2. 라우팅: 기능·계약 변경 → backend+frontend+dev-qa 3인(구조 쟁점 없음 → architect 생략)
3. Red: backend가 SearchQuery·Specs 테스트 먼저(실패 확인), frontend가 통과 시나리오(기준 카운트) 정의
4. Green: 서버 필터 + 프론트 JSON 폴백을 한 변경 단위로 구현 → Refactor
5. dev-qa: gradlew 녹색 · 경계면 표 대조 · API vs JSON 폴백 동일 카운트 → 18 리포트
6. doc-commit 반영(main+feat 동기화)

### 정상 — 혼성 (워크플로 C)
1. "가맹점 데이터에 전화번호 필드 추가하고 카드에 표시하자"
2. architect: 수집기→SSOT→마이그레이션→API→렌더 경로 결정문
3. data(수집기·JSON) → backend(V2 마이그레이션·적재기·MerchantView) → frontend(렌더) — 단계마다 dev-qa
4. 최종 dev-qa(계약·기준값) ∥ verifier(스탬프·문구) → 통과 → doc-commit

### 정상 — 긴 호흡 (Phase 0-C)
1. "백로그 F 절 순서대로 아침까지 진행해줘. 건건이 안 물어봐도 돼."
2. 조건 셋 확인 — 종료 조건(아침까지) · 승인 면제 · 착수 목록(F 절) 모두 갖춤 → 긴 호흡 진입.
3. 착수: 목록과 순서를 보여 주고 확정, 전 스위트 `EXIT=0` 확인, 시작 커밋 기록.
4. 항목마다 반복: 테스트 → Red·Green·Refactor → 푸시 게이트 → 커밋 → 푸시 → `gh run list` 확인.
5. F3(`dataVersion` 미상향)을 고치다 데이터 파일 갱신이 필요함을 발견 → **그 자리에서 고치지 않고** 목록에 적는다.
6. F 절 소진 → `reporter` 스폰 → 아티팩트 발간 → 사용자에게 주소 한 줄.

### 에러 — 긴 호흡 중 승인이 필요한 항목
1. 목록의 한 항목이 Flyway 마이그레이션(`V9__*.sql`)을 요구한다.
2. 커밋까지만 하고 **푸시하지 않는다**. 다음 항목으로 넘어간다.
3. 마감 때 리포트 4절에 결정 요청으로 올린다 — 선택지·대가·권고·되돌리는 비용을 채워서.
