# 사용처 데이터 큐레이션

가이드에 실리는 모든 목록의 원본을 만드는 절차. 데이터 스키마 상세는 `references/data-schema.md` 참조.

## 단일 진실 공급원(SSOT) 원칙

목록은 `data/*.json`에 **한 벌만** 존재한다. 페이지 본문에 같은 사실이 또 적혀 있으면 반드시 어긋난다.

가장 흔한 사고: 페이지 헤더에 "공식 안내 30곳 — 쇼핑 22 · 배달 8"이라고 적혀 있는데, 데이터에 플랫폼을 2개 추가하면 표는 32행이 되고 헤더는 30곳으로 남는다. 헤더를 고치는 것이 해결책이 아니다 — **헤더가 숫자를 담고 있는 것 자체가 결함**이며, 데이터에서 계산되어야 한다.

따라서 수집 결과를 넘길 때 개수를 문장으로 전달하지 말고, 개수가 어떻게 계산되는지를 전달한다.

## 수집 절차

### 1. 기존 데이터 로드
`data/*.json`을 먼저 읽는다. 통째로 다시 만들지 않는 이유는 두 가지다 — 이전 수집의 검증된 정보가 사라지고, 무엇이 바뀌었는지(델타)를 알 수 없게 된다. 델타는 이용자에게 유용한 정보다.

### 2. 공식 출처 순회
온라인 플랫폼은 온누리상품권 공식 홈페이지의 '온라인 전통시장관'이 기준이다. **전 페이지를 끝까지 순회한다.** 페이지네이션이 있으면 마지막 페이지까지 확인하고, 몇 페이지를 확인했는지 기록한다. 1페이지만 보고 목록을 완성했다고 판단하는 것이 가장 흔한 수집 실패다.

### 3. 항목 정규화
각 항목에 `source_url`과 `collected_on`을 붙인다. 없으면 미완성 항목이다. 언제 본 것인지 모르는 목록은 쓸 수 없다.

### 4. 판정 유도 (오프라인)
업종의 가능 여부를 감으로 정하지 않는다. `_workspace/01_policy_analysis.md`의 요건에 비추어 판정하고, 어떤 요건 때문인지를 `basis`에 남긴다. 요건이 바뀌면 판정을 다시 계산한다 — 근거가 기록되어 있어야 재계산이 가능하다.

**"조건부"는 정직한 답이다.** 이 제도는 브랜드가 아니라 점포 단위 가맹이므로, 편의점·마트·음식점 대부분은 진짜로 조건부다. 무리하게 ✓나 ✕로 밀어붙이지 않는다.

단, 조건부로 분류했으면 **확인 방법**을 반드시 함께 준다:
- 가맹점 지도에서 점포 단위 검색
- 매장 입구의 가맹점 스티커
- 카드형은 결제 직후 앱 알림으로 차감 여부 확인 (차감이 없으면 미가맹)

확인 방법 없는 "조건부"는 이용자를 그냥 버려두는 것이다.

### 5. 델타 기록
`_workspace/02_data_report.md`에 추가·삭제·변경을 구분해 기록한다. 삭제된 항목은 JSON에서는 지우되 리포트에는 남긴다 — 어제까지 쓰던 곳이 사라졌다는 사실이 이용자에게는 중요하다.

## 수집 실패를 성공으로 착각하지 않기

부분 수집을 전체로 덮어쓰면 데이터가 조용히 사라진다. 다음 규칙을 지킨다:

| 상황 | 행동 |
|------|------|
| 일부 페이지 접근 실패 | 확인된 항목만 갱신. 미확인 항목은 유지하되 `collected_on`을 **올리지 않는다** |
| 항목 수 20% 이상 급감 | 수집 실패를 의심. 자동 반영하지 말고 리더에게 보고 |
| 항목은 있는데 필드가 빈 값 | 빈 값으로 덮어쓰지 말고 기존 값 유지 |

`collected_on`을 올리지 않는 것이 핵심이다. 이 날짜는 검증관이 페이지의 "○○ 기준" 스탬프와 대조하는 기준이 되며, 확인하지 않은 항목의 날짜를 올리면 **검증되지 않은 정보에 신뢰를 부여**하게 된다.
