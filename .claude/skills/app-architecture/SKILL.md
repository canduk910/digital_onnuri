# 애플리케이션 아키텍처 — 결정을 내리고 기록하는 절차

## 구조 지도 (판단의 출발점)

```
정적 프론트(main, GitHub Pages)          백엔드(feat, NCP api.koscomlabor.cloud)
├─ index.html    ← build_index.py 산출물   ├─ Spring: SearchQuery→Specs→Service
├─ merchants.html ─ dataMode:auto ───────→ ├─ Postgres 78,734건 (Flyway)
├─ online.html    (API 우선, JSON 폴백)    └─ Docker Compose + Caddy TLS
└─ config.js
데이터 SSOT: data/*.json ← build_region_full.py 수집 → 프론트 폴백·백엔드 적재의 공통 원천
```

**불변식** (어떤 설계도 이걸 깨면 기각):
1. data/*.json = SSOT. 프론트 폴백과 DB는 그 사영 — 두 소비자가 갈라지면 안 된다.
2. 서버 필터 규칙 ≡ 프론트 JSON 폴백 규칙 (폴백 순간에도 같은 답).
3. index.html은 직접 수정 금지 — build_index.py 재생성(D-F1).
4. backend/는 feat 브랜치 전용. main = 라이브 정적.
5. 페이지의 모든 숫자·날짜는 렌더 시 계산(하드코딩 금지).

## 구현 위치 판단 기준

| 신호 | 위치 |
|---|---|
| 데이터 수십 KB·갱신 드묾·클라이언트 필터로 충분 | 프론트 직접(fetch JSON) — online.html 선례 |
| 데이터 MB급·페이징/집계 필요·전송량 문제 | 백엔드 API — merchants 선례 |
| 표시 문구·숫자 규칙 | 빌더/렌더 계산식 (콘텐츠 명세의 동적 문구 표) |
| 수집·가공 규칙 | dev_scripts (데이터 파이프라인) — 페이지·서버가 아니라 원천에서 |
| 양쪽 규칙이 필요한 필터 | **서버+폴백 동시 구현**을 하나의 변경 단위로 설계 |

새 축(예: 챗봇/RAG) 도입은 **끌 수 있는 형태**(config 스위치·별도 브랜치·폴백)로 단계 설계한다 — dataMode가 선례. 빅뱅 전환 금지, 스트랭글러로.

## 리팩토링 절차 (TDD Refactor 단계)

1. **동작 고정** — 대상의 현재 동작을 테스트/기준값으로 스냅샷(dev-testing 기준표 + 필요 시 추가 테스트). 스냅샷 없이 구조를 만지지 않는다.
2. **작게 자른다** — 한 커밋 = 한 종류의 정리(이동/추출/이름). 동작 변경과 구조 변경을 한 커밋에 섞지 않는다.
3. **사후 검증** — 같은 스냅샷 재실행 녹색 + dev-qa 경계면 확인.
4. 흔한 대상: 3페이지에 복제된 셸/칩 CSS·JS(공통화 시 index 번들 제약 고려), 긴 함수, 특수 케이스 누적 지점.

## 경량 ADR (`_workspace/16_arch_decisions.md`)

결정마다 4~8줄로 누적한다:

```markdown
## ADR-{n}: {제목} ({날짜})
- 맥락: 무엇이 문제였나 (1-2줄)
- 결정: 무엇을 어디에 (1-2줄)
- 근거: 왜 대안이 아니라 이것인가 (기각한 대안 1개 이상 명시)
- 결과·롤백: 영향 범위와 되돌리는 방법
```

기존 결정을 뒤집을 때는 새 ADR로 "ADR-x를 대체" 명시 — 조용한 번복은 다음 세션의 재논쟁을 만든다.

## 위임 결정문 (구현을 넘길 때)

backend/frontend에게 넘기는 결정문에는 반드시: ①구현 위치와 이유 ②지켜야 할 계약(필드·센티넬·상한) ③요구 테스트(무엇이 통과 조건) ④롤백 경로. 이 네 가지가 없으면 구현자가 다시 물으러 온다.
